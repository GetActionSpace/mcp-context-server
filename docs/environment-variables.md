# Environment Variables Reference

## Introduction

All configuration is via environment variables, set in a `.env` file, directly in the shell, or in your MCP client configuration (`env` block in `.mcp.json`). The canonical source of truth for all variables is the [`app/settings/`](../app/settings/) package.

MCP clients such as Claude Code support environment variable expansion using `${VAR}` or `${VAR:-default}` syntax. For details, see: <https://docs.claude.com/en/docs/claude-code/mcp#environment-variable-expansion-in-mcp-json>

## Core Settings

| Variable              | Type      | Default                       | Description                                                                                                                                                                                                                                   |
|-----------------------|-----------|-------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `LOG_LEVEL`           | string    | `ERROR`                       | Application log level. Options: `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`. The single effective verbosity control: the server aligns FastMCP's non-propagating logger tree and, on HTTP transports, uvicorn's loggers with this level   |
| `STORAGE_BACKEND`     | string    | `sqlite`                      | Database backend. Options: `sqlite`, `postgresql`                                                                                                                                                                                             |
| `DB_PATH`             | path      | `~/.mcp/context_storage.db`   | SQLite database file location. Only used when `STORAGE_BACKEND=sqlite`. Blank or whitespace-only values are rejected at startup as a configuration error (exit 78)                                                                            |
| `MAX_IMAGE_SIZE_MB`   | integer   | `10`                          | Maximum size per image attachment in megabytes (minimum `1`)                                                                                                                                                                                  |
| `MAX_TOTAL_SIZE_MB`   | integer   | `100`                         | Maximum total request size in megabytes (minimum `1`)                                                                                                                                                                                         |
| `DISABLED_TOOLS`      | string    | _(empty)_                     | Comma-separated list of MCP tools to disable (e.g., `delete_context,update_context`)                                                                                                                                                          |

On the `http`, `streamable-http`, and `sse` transports the MCP SDK rejects any request body larger than 4 MiB with HTTP 413 before a tool runs, whatever `MAX_IMAGE_SIZE_MB` and `MAX_TOTAL_SIZE_MB` allow. Images travel base64-encoded, which adds about a third to their size, so over HTTP a single image above roughly 3 MiB is refused; store larger images over the `stdio` transport. The same limit bounds a single document over HTTP; [Limits](knowledge-base.md#limits) in the Knowledge Base Guide covers it together with the response limit and the reverse-proxy settings a corpus sync needs.

## Access Control Settings

Every stored entry carries a server-stamped `owner_id` (the verified `jwt` principal, or the configured default principal for STDIO, `MCP_AUTH_PROVIDER=none` and `simple_token` requests) and a `visibility` of `private` (readable by the owner and every grantee) or `public` (readable by everyone). The server enforces both on SQLite and PostgreSQL: every read, search, thread listing and per-entry statistic covers only the entries the caller may read, content edits need ownership or a write grant, and visibility changes and deletes are owner-only; publishing as `public` may additionally require the configured role. On PostgreSQL, `ENABLE_POSTGRESQL_RLS` additionally enforces the same rules in the database through row-level security. See the [Access Model](authentication.md#access-model) for the full rules and their limits.

| Variable                              | Type    | Default               | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
|---------------------------------------|---------|-----------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `ACCESS_CONTROL_DEFAULT_PRINCIPAL`    | string  | `local`               | Principal id stamped as `owner_id` for every request without a `jwt` identity: STDIO transport and `MCP_AUTH_PROVIDER` `none` or `simple_token`. Also the owner backfilled onto rows that predate the access-control columns. Restricted to 1-128 characters from `A-Z a-z 0-9 . _ @ : + -`                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `ACCESS_CONTROL_DEFAULT_VISIBILITY`   | string  | `private`             | Visibility stamped on stored entries when the caller does not specify one. Options: `private` (owner plus every grantee), `public` (everyone)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `ACCESS_CONTROL_DEFAULT_GROUP_GRANTS` | string  | `none`                | Automatic group read grants on newly inserted entries. Options: `none` (no automatic grants), `author_groups` (every group of the writing principal receives a read grant, effective under the default `private` visibility)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `ACCESS_CONTROL_PUBLISH_ROLE`         | string  | _(none)_              | Role required to set visibility `public`. Unset lets any owner publish; set to a role name to restrict publishing to callers whose verified roles claim carries that role                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `ACCESS_CONTROL_ANONYMOUS_PRINCIPAL`  | string  | _(none)_              | Principal id of the read-only `jwt` subject, matched verbatim against the token's `sub` claim: every write tool refuses it, its groups and roles are discarded, and its token must carry `exp`. Unset makes no principal read-only. The setting fails open: a value that differs from the minted `sub` leaves that token an ordinary writable principal, so the server logs `Read-only principal: <id>` at INFO level on startup (the default `LOG_LEVEL=ERROR` hides that line), and a `store_context` call with the token must answer `The anonymous principal is read-only: store_context is not permitted` before you distribute it. Any characters are allowed; it must differ from `ACCESS_CONTROL_DEFAULT_PRINCIPAL` |
| `ENABLE_POSTGRESQL_RLS`               | boolean | `false`               | Also enforce the access model in PostgreSQL through row-level security. Requires `STORAGE_BACKEND=postgresql` and `POSTGRESQL_MIGRATION_USER` naming the role that owns the tables; requests must connect as a different role that is a member of `POSTGRESQL_RLS_POLICY_ROLE` and neither superuser nor `BYPASSRLS`. A misconfiguration fails at startup (exit 78), and so does `false` over installed policies until `mcp-context-server-migrate --disable-rls` removes them                                                                                                                                                                                                                                              |
| `POSTGRESQL_RLS_POLICY_ROLE`          | string  | `mcp_context_request` | NOLOGIN role the row-level security policies apply to. The operator creates it and grants it to the request login role (`CREATE ROLE mcp_context_request NOLOGIN; GRANT mcp_context_request TO <login>;`); the server grants it the table privileges at startup and refuses to start when it is missing. Restricted to 1-63 characters from `a-z 0-9 _`, not starting with a digit                                                                                                                                                                                                                                                                                                                                          |

When an existing deployment switches to `MCP_AUTH_PROVIDER=jwt`, the entries owned by `ACCESS_CONTROL_DEFAULT_PRINCIPAL` must be handed to the operator's IdP subject. Setting `ACCESS_CONTROL_DEFAULT_PRINCIPAL` to that subject hands them over only when the variable is set in the environment of the run that stamps their owner. For an integer-keyed v2 database, that run is the `mcp-context-server-migrate` conversion to the UUIDv7 schema, which stamps every copied entry with the value from its own environment; the first server start on the migrated database changes no owner. For a UUIDv7-keyed database whose `context_entries` table predates the access-control columns, that run is the first start of the upgraded server, which adds the columns. Both runs accept only subjects inside the character set above, which exists because the server interpolates the value into the access-control migration's DDL. A subject outside it, such as Auth0's `auth0|...` or `google-oauth2|...`, and any database that already carries the columns, take `mcp-context-server-migrate --reassign-owner` instead; for a v2 database, run it on the migrated database. See [Switching an Existing Deployment to JWT](authentication.md#switching-an-existing-deployment-to-jwt).

`ACCESS_CONTROL_ANONYMOUS_PRINCIPAL` serves one shared read-only token. [Anonymous Read Access](authentication.md#anonymous-read-access) shows how to mint that token, how to check it before you distribute it, and how `MCP_AUTH_ANONYMOUS_JWT_PUBLIC_KEY` lets a JWKS deployment accept it.

## Embedding Settings

### General

| Variable                         | Type      | Default                  | Constraints          | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
|----------------------------------|-----------|--------------------------|----------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `ENABLE_EMBEDDING_GENERATION`    | boolean   | `true`                   |                      | Enable embedding generation for stored context entries. If `true` and dependencies are not met, server will NOT start. Set to `false` to disable embeddings entirely                                                                                                                                                                                                                                                                                                                                              |
| `EMBEDDING_PROVIDER`             | string    | `ollama`                 |                      | Embedding provider. Options: `ollama`, `openai`, `azure`, `huggingface`, `voyage`                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `EMBEDDING_MODEL`                | string    | `qwen3-embedding:0.6b`   |                      | Embedding model name (provider-specific)                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `EMBEDDING_DIM`                  | integer   | `1024`                   | 1-4096, must be >0   | Embedding vector dimensions. Changing after initial setup requires database migration. On PostgreSQL with `ENABLE_EMBEDDING_COMPRESSION=false` the maximum is 2000: pgvector caps its HNSW index at 2000 dimensions for the `vector` type, and values above that are rejected at startup as a configuration error (exit 78); set `ENABLE_EMBEDDING_COMPRESSION=true` to lift this limit (compressed payloads are stored as BYTEA with no pgvector dimension cap)                                                  |
| `EMBEDDING_TIMEOUT_S`            | float     | `240.0`                  | >0, <=3600           | Timeout in seconds for one attempt of one embedding request: one batch of a document's chunks on the store/update path (see `EMBEDDING_BATCH_SIZE`), one query on search. The retries, and the total timeout the server derives from this value, `EMBEDDING_RETRY_MAX_ATTEMPTS` and `EMBEDDING_RETRY_BASE_DELAY_S`, also apply per batch, so the setting limits how long one request may take, not how large a document may be. The one-hour ceiling caps how long a stalled provider can hold one attempt open   |
| `EMBEDDING_RETRY_MAX_ATTEMPTS`   | integer   | `5`                      | 1-10                 | Maximum number of retry attempts for embedding generation                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `EMBEDDING_RETRY_BASE_DELAY_S`   | float     | `1.0`                    | >0, <=30             | Base delay in seconds between retry attempts (with exponential backoff)                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `EMBEDDING_MAX_CONCURRENT`       | integer   | `3`                      | 1-20                 | Maximum concurrent embedding requests on the store/update path. A chunked document holds one slot per batch and releases it between batches, so a waiting caller gets a slot after the current batch of a running document. Limits parallel provider requests to prevent overload                                                                                                                                                                                                                                 |
| `EMBEDDING_BATCH_SIZE`           | string    | `auto`                   | `auto` or 1-512      | Chunks per embedding request when the server embeds a chunked document. `auto` sizes each batch to take about `EMBEDDING_BATCH_TARGET_S` from the seconds per chunk measured on earlier batches (4 chunks before the first measurement, then 1 to 64); an integer fixes the size. Each batch is one provider request with its own retries and timeout, so a retry re-sends only the batch that failed                                                                                                             |
| `EMBEDDING_BATCH_TARGET_S`       | float     | `5.0`                    | >0, <=3600           | Wall time in seconds one embedding batch should take when `EMBEDDING_BATCH_SIZE=auto`. A smaller target serves waiting callers sooner and sends more requests per document; a larger one sends fewer, larger requests                                                                                                                                                                                                                                                                                             |
| `EMBEDDING_QUERY_INSTRUCTION`    | string    | _(none)_                 |                      | Instruction prefix prepended verbatim to the text embedded for search queries (`semantic_search_context` and the semantic leg of `hybrid_search_context`); document embeddings on the store/update path always stay bare. Unset or empty leaves query text unchanged. See the instruct-aware model guidance below for the default `qwen3-embedding:0.6b` deployment                                                                                                                                               |

`EMBEDDING_QUERY_INSTRUCTION` targets instruct-aware embedding models. The default `qwen3-embedding:0.6b` is one: its model card prescribes an instructed query side in the format `Instruct: {task}\nQuery:{query}`, and omitting the instruction costs roughly 1-5% retrieval quality, so the recommended value for that deployment is `Instruct: Given a web search query, retrieve relevant passages that answer the query\nQuery:` (the `\n` is a real newline and the value ends with `Query:`; the search query is concatenated directly after it). A plain `.env` line cannot carry a newline, so set multi-line values through a mechanism whose escape produces a real newline: a double-quoted YAML scalar in Docker Compose or Kubernetes manifests (`"EMBEDDING_QUERY_INSTRUCTION=Instruct: ...\nQuery:"`) or an ANSI-C quoted shell export (`export EMBEDDING_QUERY_INSTRUCTION=$'Instruct: ...\nQuery:'`). Cloud models such as OpenAI `text-embedding-3-small` need no prefix, which is why the setting is opt-in and unset by default. The instruction changes only future query vectors; stored document embeddings are untouched, and enabling or changing it requires no re-embedding.

The server embeds a chunked document in batches rather than in one request. Each batch is one provider request with its own retries and total timeout, sized by `EMBEDDING_BATCH_SIZE` and `EMBEDDING_BATCH_TARGET_S`, so a large document needs no larger `EMBEDDING_TIMEOUT_S`, and a timeout or failure message names the batch and the chunks embedded so far. [Batched Document Embedding](semantic-search.md#batched-document-embedding) describes how the server sizes and schedules the batches.

For detailed embedding setup and provider selection, see the [Semantic Search Guide](semantic-search.md). To change `EMBEDDING_MODEL` on an existing database, run the migration CLI's `--re-embed` flag; changing `EMBEDDING_DIM` requires a database rebuild. Both procedures are documented in [Changing the Embedding Model or Dimensions](migration-v2-to-v3.md#changing-the-embedding-model-or-dimensions).

| Variable                                       | Type      | Default              | Constraints   | Description                                                                                                                                                                                                           |
|------------------------------------------------|-----------|----------------------|---------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `ENABLE_INDEX_TREE_NODE_SUMMARIES`             | boolean   | `true`               |               | Generate per-node LLM summaries for the navigate_context index_tree and provision the `context_index_nodes` table. Additive/never-raise (never aborts a store)                                                        |
| `INDEX_TREE_NODE_SUMMARY_PROMPT`               | string    | (built-in)           |               | Override the per-node summary system prompt. Empty resolves to a dedicated short headline-style abstract prompt                                                                                                       |
| `INDEX_TREE_NODE_SUMMARY_MIN_CONTENT_LENGTH`   | integer   | `500`                | 0-100000      | Heading sections shorter than this (characters) skip node-summary generation (0 = always)                                                                                                                             |
| `INDEX_TREE_NODE_SUMMARY_TIMEOUT_S`            | float     | `240.0`              | > 0, <= 600   | Per-node summary timeout in seconds; a timeout omits that node, never aborts the store                                                                                                                                |
| `INDEX_TREE_NODE_SUMMARY_MAX_TOKENS`           | integer   | `120`                | 20-4000       | Output token budget of one per-node summary call (`num_predict` for Ollama, `max_tokens` for OpenAI and Anthropic), sized for a 25-word headline; an answer cut off at this budget drops that node's summary          |
| `INDEX_TREE_NODE_SUMMARY_MAX_CONCURRENT`       | integer   | `min(cpu_count,4)`   | 1-32          | Node-task launch/fan-out cap: how many per-node summary coroutines are launched concurrently. | `INDEX_TREE_NODE_SUMMARY_MAX_NODES`            | integer   | `200`                | 1-10000       | Maximum heading sections summarized for one entry. Bounds TOTAL work per store; when more sections qualify, the shallowest and longest are summarized first                                                           |
| `INDEX_TREE_NODE_SUMMARY_TOTAL_TIMEOUT_S`      | float     | `600.0`              | >0, <=3600    | Aggregate wall-clock budget for the whole per-node summary pass of one entry; on expiry the pass keeps what it produced and never aborts the store                                                                    |

Per-node summaries reuse the configured summary provider (no second client) via a dedicated short prompt, and they share the single `SUMMARY_MAX_CONCURRENT` model-concurrency budget with the flat document summary (so `INDEX_TREE_NODE_SUMMARY_MAX_CONCURRENT` only bounds how many node coroutines are launched, not how many hit the model at once). They run in-request, overlapped with embedding/compression and started right after the flat summary, and a node-summary failure or timeout never aborts the store. Set `ENABLE_INDEX_TREE_NODE_SUMMARIES=false` to keep navigation purely code-derived with no per-store LLM cost and no node table.

Concurrency caps bound how much runs at once; `INDEX_TREE_NODE_SUMMARY_MAX_NODES` and `INDEX_TREE_NODE_SUMMARY_TOTAL_TIMEOUT_S` bound how much runs in total, so a heading-dense document cannot stretch a single `store_context` request across thousands of model calls. Sections are ranked shallowest-first (then longest-first within a level) before the cap is applied, so the most structurally significant sections keep their abstracts.

## PostgreSQL Connection Pool Settings

These settings apply only when `STORAGE_BACKEND=postgresql`.

| Variable                                  | Type      | Default   | Constraints   | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
|-------------------------------------------|-----------|-----------|---------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `POSTGRESQL_POOL_MIN`                     | integer   | `2`       | >=0           | Minimum connections in the asyncpg connection pool; must not exceed `POSTGRESQL_POOL_MAX` (rejected at the configuration boundary)                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `POSTGRESQL_POOL_MAX`                     | integer   | `20`      | >=1           | Maximum connections in the asyncpg connection pool; must be at least `POSTGRESQL_POOL_MIN` (rejected at the configuration boundary)                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `POSTGRESQL_SESSION_POOLER_MAX_CLIENTS`   | integer   | `15`      | >=1           | Per-session client cap of an external session-mode pooler (Supabase Session Pooler / Supavisor); advisory startup WARNING about MaxClientsInSessionMode when `POSTGRESQL_POOL_MAX` exceeds it. Raise on larger tiers. See `docs/database-backends.md`.                                                                                                                                                                                                                                                                                                                                           |
| `POSTGRESQL_POOL_TIMEOUT_S`               | float     | `120.0`   | >0            | asyncpg connection acquire-wait timeout in seconds: how long `pool.acquire()` waits for a free connection before failing. A startup advisory (INFO) recommends keeping this at or above a floor of `max(60, 2 * POSTGRESQL_COMMAND_TIMEOUT_S)` so a slow query cannot starve waiters. Embedding generation runs OUTSIDE the connection pool and does not consume pool time, so this timeout does not need to cover embedding latency. For robustness under embedding-write load, scale `POSTGRESQL_POOL_MAX` (more connections) and `POSTGRESQL_COMMAND_TIMEOUT_S` (per-query budget) instead.   |
| `POSTGRESQL_CONNECT_TIMEOUT_S`            | float     | `60.0`    | >0            | Connection ESTABLISHMENT timeout in seconds (TCP connect plus PostgreSQL startup handshake) for each new connection the pool or the pgvector pre-check opens; distinct from `POSTGRESQL_POOL_TIMEOUT_S`, which bounds waiting for a free pooled connection. Default 60 matches the asyncpg default. MUST be strictly below `POSTGRESQL_POOL_TIMEOUT_S`: asyncpg wraps the queue wait and the dial in one acquire deadline, so an equal or larger connect budget can never elapse (the acquire deadline cancels the dial instead) and the server refuses the pair at startup.                     |
| `POSTGRESQL_COMMAND_TIMEOUT_S`            | float     | `60.0`    | >0            | Default command timeout in seconds; per-connection `statement_timeout` is `0.9 *` this value. fp32 mode (`ENABLE_EMBEDDING_COMPRESSION=false`) may need a higher value under write concurrency (SQLSTATE 57014). See `docs/database-backends.md`.                                                                                                                                                                                                                                                                                                                                                |
| `POSTGRESQL_MIGRATION_TIMEOUT_S`          | float     | `300.0`   | >0, <=3600    | Timeout in seconds for migration DDL operations (CREATE INDEX, ALTER TABLE). Default: 300s (5 minutes)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
