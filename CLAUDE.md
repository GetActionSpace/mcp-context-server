# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Quick Reference

```bash
# IMPORTANT: dev tasks need the full sync below; bare `uv sync` lacks optional
# extras and causes type-checker errors.

# Build and run
uv sync --all-extras --all-groups   # install ALL deps (REQUIRED for dev)
uv run mcp-context-server           # start server (aliases: mcp-context, python -m app.server)
uvx mcp-context-server              # run from PyPI

# Testing
uv run pytest                       # all tests
uv run pytest tests/tools/context/test_store.py -v   # one file
uv run pytest tests/tools/context/test_store.py::TestStoreContext::test_store_text_context -v   # one test
uv run pytest --cov=app --cov-report=html   # coverage
uv run pytest -m "not integration"  # fast unit/repository suite (no Docker)
uv run pytest -m integration        # real-server integration, BOTH backends (needs Docker)

# Code quality
uv run pre-commit run --all-files   # lint + type check (Ruff, mypy, pyright)
uv run ruff check --fix .           # Ruff autofix
```

Note: Real-server integration tests run against BOTH backends from one shared, backend-parametrized harness (`tests/integration/_harness/`, `MCPServerIntegrationTest`): SQLite always, and PostgreSQL via a docker-compose pgvector container (the `pg_test_url` fixture / `@requires_docker_postgres` marker; skipped automatically when Docker is unavailable).

## High-Level Architecture

### MCP Protocol Integration

[Model Context Protocol](https://modelcontextprotocol.io) (MCP) server with JSON-RPC 2.0, automatic tool discovery, Pydantic validation, multi-transport (default stdio; also HTTP, streamable-http, SSE), and tool annotations (readOnlyHint, destructiveHint, idempotentHint). Compatible with Claude Desktop, Claude Code, LangGraph, and any MCP client.

### MCP Server Architecture

FastMCP 4.1.x-based server (MCP Python SDK 2.x) providing persistent context storage for LLM agents:

1. **FastMCP Server Layer** (`app/server.py`, `app/tools/`, `app/startup/`):
   - Entry point `app/server.py`: the settings guard (the first `get_settings()` call in the import graph), FastMCP instance, `lifespan()`, `main()`, `/health` endpoint (HTTP transport only). `lifespan()` runs the startup phases in `app/startup/`, passing `settings` to each. On PostgreSQL `_start_postgresql()` first reads the request role (`rls_posture.discover_request_role()`, only when `POSTGRESQL_MIGRATION_USER` is set; `refuse_unsafe_request_role()` refuses a superuser/BYPASSRLS/non-member request role with RLS on, before any DDL), then runs `database_setup.prepare_database(maintenance, settings, request_role=)` (schema, migrations, compression validation and announcement, request-role grants, RLS) on a short-lived table-owner backend from `create_maintenance_backend()` (`split_request_role()` compares the two `current_user` values and, with RLS on, refuses one role for both), then opens the request backend and, when the roles are split, runs `rls_posture.verify_rls_posture()` in either flag state; SQLite prepares on its one backend with `request_role=None`. Then `rls_posture.warn_jwt_without_rls()`, `access.log_read_only_principal()` (the INFO line `Read-only principal: <id>` or `none`), `tool_registration.register_core_tools()`, `providers.initialize_providers()` (LangSmith, embedding, reranking, chunking, summary, Ollama prewarm), `tool_registration.register_search_tools()` (semantic/FTS/hybrid), `tool_registration.install_json_string_middleware()`; tools register via `register_tool()` from `app/tools/__init__.py`.
   - Tools in `app/tools/` by domain: `context/` (single-entry CRUD: `store.py` `store_context`, `retrieve.py` `get_context_by_ids`, `update.py` `update_context`, `delete.py` `delete_context`), `search/` (4 search tools: `browse.py` `search_context`, `semantic.py`, `fts.py`, `hybrid.py`, plus `legs.py` the raw semantic/FTS legs the standalone and hybrid tools share, `ranking.py` reranking and result display formatting, `limits.py` argument bounds and filter caps), `navigation/` (locate/navigate/extract: `grep.py` `grep_context`, `navigate.py` `navigate_context`, `read_range.py` `read_context_range`), `discovery.py` (list_threads, get_statistics), `sync.py` (the read-only corpus sync tools `plan_context_sync` and `list_ingest_state`, registered by `register_core_tools` behind `ENABLE_CONTEXT_SYNC`), `sharing.py` (the owner-only, ungated core tools `share_context`, `unshare_context` and `list_context_grants`, one entry per call: share is idempotent, unshare removes exactly the named `(principal_type, principal_id, permission)` row and reports `remaining_permissions`, list neither pages nor caps; the private `_run_owned_grant_change` runs probe, owner check and grant change in one transaction with a bounded connection-error retry), `batch/` (batch CRUD: `store.py`, `update.py`, `delete.py`, plus `entry_validation.py`, the per-entry validation shared by the batch store and update tools, and `update_access.py`, the batch update's write-access checks: `authorize_updates` before generation and `reraise_disambiguated_cas_conflict` for a compare-and-set that matched zero rows), `descriptions.py` (backend-specific dynamic descriptions), and the internal infrastructure modules used by `context/`/`batch/` (input validation also by `search/`/`navigation/`), none re-exported via `__init__.py`: `_validation.py` (per-entry input validation: unstorable text, tag limits, indexed metadata values, image validation), `_generation.py` (concurrent generation orchestration via `run_generation` — the embedding→compression leg `embed_then_compress`, the flat summary leg `generate_summary_with_timeout`, and the overlapped node-summary leg `_nodes_after_summary` — plus the generation semaphores), `_transactions.py` (store/update transaction execution, transaction heartbeat, connection-error classification), `_delete_cleanup.py` (delete-path embedding cleanup), `_responses.py` (response builders), `_sync_plan.py` (the pure, I/O-free sync diff behind `plan_context_sync`: `stored_member`, `manifest_error`, `compute_sync_plan`).
   - Global state/init in `app/startup/`: `init_database()`, `ensure_repositories()`, `set_summary_provider()`/`get_summary_provider()`. The package `__init__` never imports the phase modules (`tool_registration` imports `app.tools`, which imports `app.startup`).
   - **Middleware** (`app/middleware/`): schema-aware `JsonStringDeserializerMiddleware` (FastMCP 4.1.x Middleware API, `on_call_tool` override), a workaround for MCP clients (including Claude Code) that intermittently serialize list/dict parameters as JSON strings. `build_schema_map()` inspects each tool's JSON Schema at startup for `array`/`object` params (incl. `Optional` via `anyOf`/`$ref`) — only those are deserialization candidates, strings are never touched; handles double-encoding. Registered via `mcp.add_middleware()` by `install_json_string_middleware()` (`app/startup/tool_registration.py`), which `lifespan()` calls after every `register_tool()` call. Its upstream tracking and removal trigger live in the upstream-issue index (see "Upstream Workarounds").

2. **Authentication Layer** (`app/auth/`): HTTP-transport auth via `MCP_AUTH_PROVIDER`; architecturally inert on stdio (`create_auth_provider()` is only called for non-stdio transports, so misconfigured auth never blocks a stdio start). `simple_token.py`: static bearer token, constant-time comparison (`MCP_AUTH_TOKEN`). The `jwt` provider (factory arm in `__init__.py`) verifies IdP-issued JWTs through fastmcp's `JWTVerifier` — static PEM key/HS secret OR JWKS URI (exactly one; validated in the factory, NOT in pydantic, to preserve stdio inertness), optional issuer/audience pinning, `MCP_AUTH_JWT_*` env vars; it checks `exp` only when present and never `nbf`, so a token without `exp` never expires (documented; refused only for the anonymous principal, below). On a JWKS deployment `MCP_AUTH_ANONYMOUS_JWT_PUBLIC_KEY` adds `anonymous.py`'s `AnonymousSubjectVerifier` (a `JWTVerifier` over an operator-held static key, pinning the same issuer and audience, accepting only the `ACCESS_CONTROL_ANONYMOUS_PRINCIPAL` subject), built by `_create_anonymous_verifier` and composed as `MultiAuth(verifiers={'anonymous': ..., 'jwt': ...})`, anonymous first; the key without `MCP_AUTH_JWT_JWKS_URI` or without the anonymous principal is a `ConfigurationError` (exit 78), and `anonymous.py` is imported only inside the jwt arm. `claims.py`: IdP-agnostic claim extraction (flat, dotted-path, and full-URL claim keys; Entra ID group-overage fail-closed to empty groups, no Graph call). `principal.py`: `RequestPrincipal(principal_id, groups, roles)` resolved per-request from `fastmcp.server.dependencies.get_access_token()` (`sub` claim, else the token's `original_client_id or client_id`, so `MultiAuth`'s source-qualified `client_id` never renames a principal; fastmcp's client id is `client_id`, `azp`, `sub` or `unknown`) ONLY when `MCP_AUTH_PROVIDER=jwt`; it returns `None` for every other request — stdio, `none`, AND `simple_token`, whose bearer token proves access but names no principal (`MCP_AUTH_CLIENT_ID` identifies the client to FastMCP and is NOT an owner identity); `RequestPrincipal.access_scope()` returns `AccessScope(principal_id, groups)` (roles only gate publishing). `access.py`: access-control policy — `resolve_effective_principal()` maps the no-principal case to `ACCESS_CONTROL_DEFAULT_PRINCIPAL` (empty groups/roles) so every request resolves to exactly one owner identity, and for the read-only principal (`is_read_only(principal)`: `ACCESS_CONTROL_ANONYMOUS_PRINCIPAL` set and equal to `principal_id`, verbatim, so the setting fails open when unset or mistyped) discards its groups and roles and raises `ToolError` when its token's `expires_at` is None; `resolve_access_scope()` returns that principal's scope (each read tool, `list_context_grants` included, calls it once at entry, before prefix resolution; the eight non-read-only tools (both stores, both updates, both deletes, `share_context`, `unshare_context`) call `resolve_effective_principal()` and then `reject_read_only_principal(principal, tool=...)` as their first statements (the publish gate needs the roles, the read-only gate the principal), and derive the scope with `resolve_write_scope(principal)`, which sets `AccessScope.may_publish` from `may_publish(principal)` and `may_write` to `not is_read_only(principal)`), `visibility_denied_reason()` enforces the `ACCESS_CONTROL_PUBLISH_ROLE` publish gate through the same `may_publish()` (False for the read-only principal), and `log_read_only_principal()` logs the startup line. Reads, updates, deletes and grant changes are scoped to the effective principal on both backends, and on PostgreSQL with `ENABLE_POSTGRESQL_RLS` also by row-level security (see "Access Scoping"). Sharing is owner-only (`app/tools/sharing.py`; a write grant never extends access), and every entry-carrying read response reports `visibility` and `is_owner` but never `owner_id`; operators mint the shared anonymous token with the recipe in `docs/authentication.md` ("Anonymous Read Access"), which `tests/docs/test_anonymous_token_recipe.py` runs over seven algorithms.

3. **Storage Backend Layer** (`app/backends/`):
   - **StorageBackend / TransactionContext Protocols** (`base.py`): database-agnostic interface (9 methods incl. `begin_transaction()` and `readable_relation(table, *, alias)`); `execute_read`, `execute_write` and `begin_transaction` take a REQUIRED keyword-only `access_scope: BackendAccess` (see "Access Scoping"), and `base.py` also defines `MaintenanceAccess`/`MAINTENANCE`, `BackendAccess`, `ROUTABLE_TABLES` and `base_relation()`. `TransactionContext` exposes `connection`/`backend_type` for atomic multi-op transactions.
   - **SQLiteBackend**: zero-config, connection pooling, write queue, circuit breaker, single-user. Package `app/backends/sqlite_backend/`: `SQLiteBackend` is assembled in `__init__.py` from flat mixins (`write_queue.py`, `health.py`, `connection_scopes.py` for `get_connection` and reads, `transactions.py`, `lifecycle.py`) over `SQLiteConnectionsMixin` (`connections.py`: connection creation and teardown, PRAGMAs, sqlite-vec load) and `SQLiteBackendCore` (`core.py`: state, metrics); helpers in `contention.py` (`is_sqlite_locked_error`), `resilience.py`, `config.py`.
   - **PostgreSQLBackend**: async via asyncpg, connection pooling, MVCC, JSONB/GIN indexes, pgvector, Pgpool-II auto-detection (warns to set `POSTGRESQL_STATEMENT_CACHE_SIZE=0`). Sends NO startup-packet parameters: `search_path`, `extra_float_digits` and the TCP keepalive GUCs are applied as `SET` statements (`session_guc_set_statements` / `apply_session_gucs` in `app/backends/postgresql_backend/session.py`) by the pool setup callback on every acquire — which also restores them after the pool's `RESET ALL` — and by each one-off connection right after dialing, so an external pooler cannot refuse a connection over a non-allowlisted startup parameter. Package `app/backends/postgresql_backend/`: `PostgreSQLBackend` is assembled in `__init__.py` from flat mixins (`provisioning.py`, `lifecycle.py`, `operations.py` for `get_connection` and `execute_read`/`execute_write`, `transactions.py`) over `PostgreSQLBackendCore` (`core.py`); helpers in `session.py` (connection kwargs incl. the migration-credential override, identifier quoting, session GUCs), `session_profiles.py` (the constructor-injected `SessionProfile`: `UnboundProfile` for RLS off, base names, no bind and no read transaction; `RlsRequestProfile` for RLS on, `BIND_IDENTITY_STATEMENT` first in every transaction, reads wrapped in a transaction, `context_entries` read through `context_entries_readable`; `MaintenanceProfile` for the table-owner backend, no bind, base names, `SET row_security = off` on every acquire), `pool_callbacks.py` (asyncpg connect/setup/init/reset callbacks), `acquire_faults.py`, `resilience.py`. An `InsufficientPrivilegeError` (42501) inside a body is logged with its SQLSTATE and operation name, breaker-exempt and not retried: startup verified the privileges, so it means the app and a policy disagree. In both backend packages `__init__.py` binds only the backend class: import every other name from its defining submodule and patch `settings` in the submodule that reads it (`tests.helpers.rebind_package_settings()` rebinds a whole package).
   - **Backend Factory** (`factory.py`): `create_backend()` creates the request backend from `STORAGE_BACKEND`, its profile chosen by `ENABLE_POSTGRESQL_RLS`; `create_maintenance_backend()` builds the backend migrations, startup and the CLI run on: PostgreSQL over the request connection settings with `POSTGRESQL_MIGRATION_USER`/`POSTGRESQL_MIGRATION_PASSWORD` overriding user and password, each only when set (an explicit `connection_string`, the CLI's, keeps its own credentials), or the SQLite backend.

4. **Repository Pattern** (`app/repositories/`): **RepositoryContainer** (`__init__.py`) = DI container. ### Thread-Based Context Management

Agents share context via `thread_id`. Entries tagged `source`: 'user' or 'agent'. Filter by thread, source, tags, content type, or metadata (16 operators). Flat structure (no hierarchy). A knowledge-base corpus is one thread `kb:<corpus>` with `source='user'`; its managed entries carry the reserved `metadata.ingest` block `{scope, source_id, meta_digest, synced_at}` (validated for shape on every write before generation; never part of an access decision), and an entry is a member of thread T exactly when its block is valid and `scope == T`, decided at read time. Guide: `docs/knowledge-base.md`.

### Database Schema

Tables: `context_entries` (main; thread_id/source indexes, JSON metadata, summary column), `tags` (many-to-many, lowercase, UNIQUE on `(context_entry_id, tag)` — tags are a SET per entry; the write path normalizes and deduplicates through `app/models.py::normalize_tag_list`, the single definition of what makes two tags the same label, and the inserts carry `ON CONFLICT DO NOTHING` on that index), `image_attachments` (binary, cascade delete), `context_entry_grants` (per-entry access grants: `principal_type` user|group, `principal_id`, `permission` read|write, `granted_by`, UNIQUE on `(context_entry_id, principal_type, principal_id, permission)` with `ON CONFLICT DO NOTHING` idempotent inserts; SQLite keeps the base schema's TEXT FK ON DELETE CASCADE; PostgreSQL also carries `entry_owner_id` (the entry's owner, NOT NULL) and replaces the single-column UUID FK with the composite `context_entry_grants_entry_owner_fkey (context_entry_id, entry_owner_id) REFERENCES context_entries (id, owner_id) ON UPDATE CASCADE ON DELETE CASCADE` onto the unique index `idx_context_entries_id_owner`, all three provisioned only by the grant owner migration (see "Migration System"), so the column follows every ownership change, `--reassign-owner` included, and costs nothing on updates that keep `(id, owner_id)`), `context_index_nodes` (index_tree per-node summaries; FK to `context_entries(id)` ON DELETE CASCADE — TEXT on SQLite, UUID on PostgreSQL; created only when `ENABLE_INDEX_TREE_NODE_SUMMARIES` is on).

**Access-control columns (`owner_id`, `visibility`)**: `context_entries.owner_id` (TEXT NOT NULL, no default in the base schema) is the server-stamped effective principal — the verified `jwt` principal, or `ACCESS_CONTROL_DEFAULT_PRINCIPAL` for stdio, `none` and `simple_token` requests (`app/auth/access.py::resolve_effective_principal`) — and is NEVER a tool parameter; ownership is immutable through the tools (only the operator CLI `mcp-context-server-migrate --reassign-owner` rewrites it; with RLS on the guard trigger also enforces it in the database). `visibility` (TEXT NOT NULL DEFAULT 'private', CHECK IN ('private','public')) has exactly two values: 'private' (readable by the owner and every grantee) and 'public' (readable by everyone); a grant is effective under either value and a write grant implies read. It is settable via the optional `visibility` parameter on the four store and update tools: owner-only on updates, gated by `ACCESS_CONTROL_PUBLISH_ROLE` for 'public' (`visibility_denied_reason`, applied to the EFFECTIVE value, so a caller-omitted visibility defaulting to 'public' is still gated), and applied on INSERT only for stores — a dedup UPDATE never changes owner or visibility, and the dedup COALESCE leg deliberately excludes both columns. `ACCESS_CONTROL_DEFAULT_GROUP_GRANTS=author_groups` additionally writes a read grant per author group into `context_entry_grants` inside the same store transaction (`GrantRepository.store_group_read_grants`, fresh INSERTs only), effective under the default 'private'; `share_context` writes user and group grants of either permission for the entry's owner, and tests still seed rows the tools refuse or that must bypass the seams under test with `tests/helpers.py::insert_grant` (which stamps `entry_owner_id` on PostgreSQL). Lookup indexes: `(owner_id)`, `(owner_id, thread_id)`, partial WHERE `visibility='public'`, grants `(principal_type, principal_id, context_entry_id)`; they serve the arms of the access predicate. SQLite alone also gets three covering indexes from the same migration, `idx_context_access_thread (thread_id, source, owner_id, visibility, id, content_type)`, `idx_context_access_source (source, owner_id, visibility, id)` and `idx_context_access_id (id, owner_id, visibility)`, because the predicate's grant EXISTS arm keeps SQLite from answering the OR through index lookups and `owner_id`/`visibility` follow `text_content` in the row, so a scoped scan would otherwise walk every row's text overflow pages; for the same reason the SQLite `get_statistics` tag, image and index_tree node counts match child rows against the readable parent ids (`build_readable_parent_predicate`) instead of joining the parent row, and the FTS indexed count matches the FTS5 index's `context_entries_fts_docsize` rows against the readable `rowid_int` values, because a query on the external-content `context_entries_fts` table without MATCH passes through to `context_entries` and reads each row's text. `tests/migrations/test_access_control_sqlite_plans.py` traces every statement the `get_statistics` tool runs and pins each one that names `context_entries` to a covering access index; the summary count is the one exception, since it reads the `summary` column, which no index carries. `owner_id` is internal (absent from `CONTEXT_ENTRY_COLUMNS`, never returned); `visibility` is in `CONTEXT_ENTRY_COLUMNS` (rendered by `entry_columns(alias)` in `context_repository/records.py`), and every entry-carrying read response reports it with `is_owner`, the OWNER predicate's `admits_expression()` selected per statement and coerced to bool by `entry_access_fields` in `app/tools/_responses.py`; every read, update and delete enforces both columns (see "Access Scoping").

**Ingest index (`idx_context_ingest`)**: a partial expression index serving the two sync reads, `WHERE <metadata.ingest.source_id> IS NOT NULL`, so it stays empty until a managed entry exists. SQLite covers every column the reads use (`thread_id`, `source_id`, `id`, `scope`, the block, `content_hash`, `owner_id`, `visibility`); PostgreSQL keys `(thread_id, (metadata #>> '{ingest,source_id}') COLLATE "C", id)`. It is migration-only on BOTH backends and NEVER declared in a base schema file: the SQLite key names columns the content-hash and access-control migrations add on an in-place upgrade, so a base-schema declaration would fail `init_database` on every older database. `ingest_index_ddl` renders it from the same `app/ingest_sql.py` fragments the reads use, so query and index expressions always match; the name avoids the `idx_metadata_*`/`idx_thread_metadata_*` prefixes the metadata index reconciler owns. PostgreSQL alone also gets the extended statistics `stat_context_ingest_scope (mcv, dependencies) ON thread_id, (<scope_sql('postgresql')>)` (`ingest_statistics_ddl` in `app/migrations/ingest.py`, the expression taken from `scope_sql` so it is the one the reads compare): the reads require `scope = ce.thread_id` while binding the thread, the planner rewrites that to the scope expression against the bound thread id, and without statistics on the expression it estimates a fraction of a percent of a corpus thread's rows and plans the owner pages as an owner-index or bitmap fetch plus a Sort instead of an ordered walk of the index. SQLite gets no statistics object; instead both reads name the index, `FROM <the self._readable(...) relation> INDEXED BY idx_context_ingest` (`_index_hint` in `context_repository/ingest.py`, an empty string on PostgreSQL), because once `sqlite_stat1` exists (`ANALYZE`, or the `PRAGMA optimize` the writer runs on close) its per-index averages make `idx_context_owner_thread`/`idx_thread_id` look more selective for a corpus thread far larger than the average thread; a statement whose constraints could not use the named index would fail to prepare, and the index exists on every database `prepare_database` prepared. Pinned by `tests/migrations/test_ingest_sqlite_plans.py` (a database without `sqlite_stat1` and a skewed one after `ANALYZE`: every read `SEARCH ce USING INDEX idx_context_ingest` with no temp B-tree) and `tests/integration/postgresql/test_ingest_plan_shapes_postgresql.py` (a skewed corpus after `ANALYZE`, custom and generic plans, through the read view with RLS on and the base table with RLS off: both owner pages an `Index Scan` of `idx_context_ingest` with no `Sort`/`Incremental Sort` node, the range read an index condition); `tests/integration/postgresql/test_ingest_index_postgresql.py` pins the statistics object (kinds `e`, `f` and `m`, its `pg_stats_ext`/`pg_stats_ext_exprs` rows after `ANALYZE`, no second build, the rebuild and resampling of a dropped object). PostgreSQL 14 is the floor (expression statistics), documented in `docs/database-backends.md`.

**PostgreSQL row-level security objects** (only with `ENABLE_POSTGRESQL_RLS=true`; rendered by `app/migrations/rls_ddl.py`, all in `POSTGRESQL_SCHEMA`): ENABLE (never FORCE) on the MANAGED tables (`context_entries`, `context_entry_grants`, `tags`, `image_attachments`, `embedding_metadata`, `vec_context_embeddings`, `vec_context_embeddings_compressed`, `context_index_nodes`, whichever exist), with PERMISSIVE per-command policies `<table>_<command>` `TO` the NOLOGIN policy role `POSTGRESQL_RLS_POLICY_ROLE` only (never PUBLIC): `context_entries` read = READ, insert = owner is the caller AND (not 'public' OR may publish) AND may write (the read-only principal's only database write path, closed), update = WRITE, delete = OWNER; grants read = the caller's own user/group grants OR every grant whose `entry_owner_id` is the caller, insert = `granted_by` and `entry_owner_id` both the caller, delete = `entry_owner_id` the caller, all three sublink-free (a grants policy that read `context_entries` would recurse through its READ policy, and one over the read view would break the FTS rebuild and the view lifecycle, which is why the owner arm needs the migration-provisioned `entry_owner_id`; the composite FK proves the pair exists, and RI checks bypass RLS under ENABLE); child read = readable parent, insert/delete = writable parent; no child or grants UPDATE policy. Helpers `mcp_context_principal_id()`, `mcp_context_groups()`, `mcp_context_may_publish()`, `mcp_context_may_write()` (SECURITY INVOKER, STABLE, PARALLEL SAFE, NULLIF over the transaction-local `app.*` GUCs, fail closed): SQL-standard `RETURN` bodies with NO SET clause, so the planner inlines them into every policy and view condition (a `SET search_path` clause would block inlining and cost a function call per grants row), created by `_create_helpers` in `app/migrations/rls.py` after `PIN_SEARCH_PATH` (`SET LOCAL search_path = pg_catalog, pg_temp`), which binds the names in their bodies at creation, and followed by `restore_search_path` so the fingerprints read the usual deparse. Guard trigger `guard_context_entry_access_columns` (BEFORE UPDATE OF owner_id, visibility): immutable `owner_id`, owner-only visibility, publish gate; a NULL principal (maintenance) is exempt. Read view `context_entries_readable`: owner-owned, neither `security_barrier` nor `security_invoker`, WHERE the READ policy text with the role gate `pg_has_role(CURRENT_USER, '<policy role>', 'USAGE')` folded into its identity operands and its public arm as once-per-statement scalar subqueries (`build_gated_read_predicate` in `app/access_scope.py`; a gate as a conjunct of its own would be a One-Time Filter above every join with the view, which keeps the planner from memoizing the view side of the join and costs the tags aggregates their tag-ordered plan), SELECT for the policy role only, read-only through the `reject_writes` INSTEAD OF trigger. `compression_metadata` stays outside RLS (SELECT for the policy role). Every object carries a `mcp-context-server rls v1 sha=... def=...` fingerprint comment (each `_read` policy also `preenabled=`).

**Public primary key (`context_entries.id`)**: 32-character lowercase hex UUIDv7. SQLite: `TEXT NOT NULL UNIQUE`; PostgreSQL: native `UUID NOT NULL PRIMARY KEY`. All foreign keys (`tags.context_entry_id`, `image_attachments.context_entry_id`, `embedding_metadata.context_id`, `embedding_chunks.context_id`, `vec_context_embeddings.context_id`) reference `context_entries(id)` — TEXT on SQLite, UUID on PostgreSQL.

**SQLite `rowid_int` surrogate**: on SQLite, `context_entries` carries an extra `rowid_int INTEGER PRIMARY KEY AUTOINCREMENT` — a stable INTEGER rowid backing the FTS5 external-content table, immune to VACUUM renumbering, never exposed at the MCP boundary. PostgreSQL needs no equivalent (its native `UUID` PRIMARY KEY is layout-independent).

**Embedding chunk and vec0 INTEGER bridge (preserved)**: chunking maintains a 1:N context→embedding mapping via `embedding_chunks` with INTEGER rowid bridges to vec0. `embedding_chunks.id`, `embedding_chunks.vec_rowid`, `vec_context_embeddings.id` stay INTEGER/BIGSERIAL; only the outer `context_id` FK is TEXT/UUID.

**Optimistic-concurrency `version` column**: `context_entries.version` is a monotonic token (`INTEGER` on SQLite, `BIGINT` on PostgreSQL; `NOT NULL DEFAULT 0`) backing the compare-and-set guard on the update write path (see "Update Context and Batch Operations"). It lives in the BASE schema files (`app/schemas/sqlite_schema.sql`, `app/schemas/postgresql_schema.sql`), so fresh databases and the migrate CLI target (built from the base schema) get the column directly, and an idempotent `ALTER TABLE ... ADD COLUMN` migration (`app/migrations/version.py`, run at startup) backfills it on an in-place upgrade of a database predating the column — a no-op on fresh DBs (historical rows take the `DEFAULT 0`). It is internal: never exposed at the MCP boundary and intentionally absent from `CONTEXT_ENTRY_COLUMNS`.

**Performance**: WAL mode, 256MB mmap, compound index (thread_id, source). Indexed metadata: `status`, `agent_name`, `task_name`, `project`, `report_type`. See "Metadata Field Indexing by Backend" for per-backend details.

**Optional compressed embedding storage**: with `ENABLE_EMBEDDING_COMPRESSION=true`, the fp32 `vec_context_embeddings` table is REPLACED by `vec_context_embeddings_compressed` (BLOB on SQLite, BYTEA on PostgreSQL) plus a singleton `compression_metadata(id INTEGER PRIMARY KEY CHECK (id = 1), provider, bits, variant, seed, dim, codebook_fingerprint, created_at)` provenance row. The `CHECK (id = 1)` singleton blocks accidental duplicate rows (the rotation seed is load-bearing). `codebook_fingerprint` (nullable TEXT) is the lowercase-hex SHA-256 of the REALIZED `numpy.linalg.qr` rotation matrix recorded at first compression; the validator re-derives and compares it to catch a cross-host BLAS/LAPACK/CPU QR divergence (the same `(dim, seed)` materializing a different rotation) the seed alone cannot — the compression migration adds the column to an in-place-upgraded pre-fingerprint table idempotently (SQLite PRAGMA-probe + `ALTER`, PostgreSQL `ADD COLUMN IF NOT EXISTS`). Under compression the server path does NOT provision the fp32 `vec_context_embeddings` table at all (see "Embedding storage is provisioned from `ENABLE_EMBEDDING_GENERATION`"). On PostgreSQL, `idx_vec_context_embeddings_hnsw` is dropped during `--compress` and recreated during `--decompress`. Compressed payloads have no fixed width (depends on `dim`/`bits`/`variant`); wire format (magic prefix, variant code, per-variant headers incl. the IP variant's explicit 1-byte `mse_bits` the decoder reads directly) is detailed in `docs/embedding-compression.md`.

### Search Tools

`search_context` (exact keyword), `semantic_search_context` (vector similarity), `fts_search_context` (linguistic + snippets), `hybrid_search_context` (RRF fusion of FTS + semantic).

**FTS modes**: `match` (default, stemming), `prefix` (autocomplete), `phrase` (exact order), `boolean` (AND/OR/NOT). SQLite: FTS5 with BM25, Porter stemmer. PostgreSQL: tsvector/tsquery with ts_rank_cd, 29 languages. Every search is scoped to the caller's readable entries in SQL before LIMIT and the rank depth, but SQLite `bm25()` draws on whole-index statistics, so on SQLite `fts_score` (and the hybrid FTS leg's order) shifts with entries the caller cannot read while membership and page fill do not — an accepted residual, documented in `docs/authentication.md`, `docs/database-backends.md`, the `fts_search_context` description (`app/tools/descriptions.py`, mirrored in its docstring) and the `hybrid_search_context` docstring (that tool's served description), pinned by a two-principal test, with both served descriptions pinned by `tests/tools/test_descriptions.py`; PostgreSQL `ts_rank_cd` is per-document, and the docs recommend PostgreSQL for multi-principal deployments.

**Hybrid search**: RRF `score(d) = Σ(1 / (k + rank_i(d)))`. Parallel execution, graceful degradation. Adaptive FTS: queries with ≥ `HYBRID_FTS_OR_THRESHOLD` (default 4) significant terms switch AND→OR for better recall.

**Ranked pagination**: the three ranked tools (semantic, FTS, hybrid) decide their order after the database answers (reranking, RRF, or both), so every page is a window into ONE ordering computed over a FIXED candidate depth (`RANKED_SEARCH_DEPTH` = `MAX_SEARCH_LIMIT` = 100 in `app/tools/search/limits.py`), independent of the requested `limit`/`offset`. A window reaching past the depth is served short and the response says so via `rank_depth_limit`; an offset at or past the depth is answered from the arguments alone, running no search and no embedding call (a structurally invalid filter still takes precedence and falls through to the normal reporting path). `fts_search_context` and `hybrid_search_context` bound their `query` at `MAX_FTS_QUERY_LENGTH` (10,000 characters), since that text is handed to a search engine that builds an expression from it; the semantic-only tool is unbounded (its query goes to an embedding provider).

**Response**: `results` (array), `count` (int), `stats` (only when `explain_query=True`).

### Navigation Tools (Locate / Navigate / Extract)

Complementary to search, sharing one Unicode code-point char-offset contract (`grep_context` match offsets and `navigate_context` node offsets both feed `read_context_range`):

- `grep_context` — server-side grep: literal/regex, line-oriented, UNRANKED matching over `text_content` (NOT FTS — no stemming/ranking). Two-stage engine: a NEW exhaustive keyset `ContextRepository.grep_scan_text_contents()` (id DESC, NOT `search_contexts` which caps at LIMIT 50) + a portable pure-ASCII `LIKE`/`ILIKE` pre-narrow, then authoritative Python matching — stdlib `re` for literal patterns, the third-party `regex` engine for user regular expressions (whose `timeout` bounds catastrophic backtracking) — the only backend-parity-safe choice (SQLite has no `REGEXP`, its `LIKE` is ASCII-only; PG POSIX dialect differs). ripgrep-style `output_mode` (files_with_matches | content | count), `-i`/`-C`, bounded `max_matches` + `truncated`, per-entry ReDoS timeout for `is_regex`.
- `navigate_context` — code-derived Markdown-heading index_tree computed ON DEMAND (`app/services/outline_service.py`): hierarchical `OutlineNode` tree, fenced-code aware, synthetic root spanning the doc whose `summary` mirrors the entry summary BY REFERENCE; `node_id` = heading-path slug + sibling ordinal. Never stale, works for every entry. `include_node_summaries=True` surfaces stored per-node LLM summaries.
- `read_context_range` — partial read of one entry by char range, line range, or `node_id`; slices full `text_content` (generation-independent), CLAMPs out-of-range offsets and ECHOES the resolved span.

**index_tree per-node summaries (ON by default, `ENABLE_INDEX_TREE_NODE_SUMMARIES`)**: the optional LLM layer stored in `context_index_nodes`. Generated IN-REQUEST. On the single-entry `store_context`/`update_context` path this is the never-raise node leg of `run_generation` (`_nodes_after_summary` in `_generation.py`): the leg starts right AFTER the flat document summary completes (flat-summary precedence) and runs OVERLAPPED with the embedding→compression leg rather than as a sequential post-compression tail; the batch paths instead generate the same node summaries via a separate `generate_index_nodes_with_timeout` per-entry pass (no `run_generation` overlap). It reuses the summary provider via `SummaryProvider.summarize_with_prompt()` with a dedicated short prompt and draws on the SHARED summary-model budget (the `_summary_model_semaphore` sized by `SUMMARY_MAX_CONCURRENT`, also held by the flat summary), so peak concurrency on the single summary model is capped regardless of overlap; `INDEX_TREE_NODE_SUMMARY_MAX_CONCURRENT` is only the node-task launch/fan-out cap. Each per-node call carries its own output budget, `INDEX_TREE_NODE_SUMMARY_MAX_TOKENS` (default 120, sized for a headline), and an answer that runs to it is dropped like a failed node, so a model looping on one section never spends `SUMMARY_MAX_TOKENS`. The aggregate node budget bounds the RUNNING chunk (outstanding node summaries are canceled and awaited when it expires), not only the gaps between chunks. A node-summary failure/timeout NEVER aborts a store (`None` preserves existing nodes, `[]` clears them, a list replaces), and on any abort-mandatory failure of the embedding or flat-summary leg the node leg is canceled and awaited before the transaction opens (no orphaned model call). Surviving node rows are still written atomically inside the same store/update transaction via `IndexNodeRepository.replace_nodes_for_context` (which pre-checks table existence so a missing table is a no-op, never an abort).

### Migration System

Auto-applied idempotent migrations in `app/migrations/`: semantic search, FTS, chunking (1:N embeddings), metadata indexing, summary column, content_hash column, version column (`context_entries.version` optimistic-concurrency token; idempotent `ALTER TABLE ... ADD COLUMN` so an in-place upgrade of a database predating the column gains it — a no-op on fresh DBs whose base schema already has it), access control (`app/migrations/access_control.py`: unconditional; `owner_id`/`visibility` columns via single-statement `ADD COLUMN ... NOT NULL DEFAULT` — the fail-closed backfill: existing rows get `visibility='private'` and owner `ACCESS_CONTROL_DEFAULT_PRINCIPAL`, whose value is re-validated against `SAFE_PRINCIPAL_ID_PATTERN` immediately before DDL interpolation — plus the `context_entry_grants` table and the access lookup indexes; the lingering column default on upgraded DBs is inert because the application always stamps `owner_id` explicitly), ingest index (`app/migrations/ingest.py` `apply_ingest_index_migration`, unconditional, right after the access-control migration because the SQLite key names its columns: SQLite runs the `IF NOT EXISTS` DDL; PostgreSQL first probes `pg_index` for an index of that name and `pg_statistic_ext` for the statistics object `stat_context_ingest_scope` (`stxrelid = to_regclass('context_entries')`), both on the `context_entries` table `to_regclass('context_entries')` resolves through the configured search_path, so a same-named index or statistics object in another schema never skips the build, and a boot that finds both takes no lock and runs no DDL and no `ANALYZE`; otherwise one `begin_migration` under the advisory lock and `POSTGRESQL_MIGRATION_TIMEOUT_S` builds whichever is missing, a created statistics object followed by `ANALYZE context_entries` so it describes the table before the first request, after which autovacuum's analyze keeps it current), grant owner (`app/migrations/grant_owner.py` `apply_grant_owner_migration`, right after the ingest index migration and before tag uniqueness, request-role grants and RLS; a no-op on SQLite; on PostgreSQL the ONLY provisioner of `context_entry_grants.entry_owner_id`, the unique index `idx_context_entries_id_owner (id, owner_id)` and the composite FK `context_entry_grants_entry_owner_fkey`, migration-only like the ingest index because the base schema runs on every boot against databases whose `context_entries` may predate `owner_id`, so neither `app/schemas/postgresql_schema.sql` nor `access_control.py` declares them; a lock-free probe through the search_path (column NOT NULL, index, FK) skips a complete database with no lock and no DDL, otherwise one `begin_migration` under the advisory lock re-probes and builds the index, adds and backfills the column, sets NOT NULL, drops the single-column FK found by its column in `pg_constraint` and adds the composite one, logging `Grant owner migration applied: <n> grants backfilled`; with RLS on, an upgrade to a release that changes the policies is a full stop of every instance, because an older instance refuses the newer grants policies and fails NOT NULL on `entry_owner_id`, documented in `docs/database-backends.md`), index_tree (`context_index_nodes`, gated on `ENABLE_INDEX_TREE_NODE_SUMMARIES`), tag uniqueness (`app/migrations/tag_uniqueness.py`: skipped outright when the `idx_tags_entry_tag` UNIQUE index already exists — the index is the completion marker, so fresh databases and every post-upgrade boot do no table work; on a genuine upgrade it deletes duplicate `tags` rows keeping the lowest id per `(context_entry_id, tag)` via a correlated EXISTS self-join (NOT a `NOT IN` over a grouped subquery, which PostgreSQL degrades to a quadratic subplan rescan on large tables), then creates the UNIQUE index the base schema declares — the delete is the only thing that repairs entries stored with a repeated label before the write path deduplicated). PostgreSQL DDL uses `POSTGRESQL_MIGRATION_TIMEOUT_S` (300s). Changing `FTS_LANGUAGE` requires an FTS table rebuild.

**Row-level security and request-role grants** (PostgreSQL; every migration runs on the maintenance backend as the table owner and passes `MAINTENANCE`): `guard_rls_disable_over_enabled` (`app/migrations/rls_removal.py`) runs right after the compression disable guard and refuses the flag off while any policy of ours or the read view exists (exit 78). The last two steps of `prepare_database(backend, settings, *, request_role)` (keyword REQUIRED, no default) are `apply_request_role_grants` (`app/migrations/request_role_grants.py`: whenever the roles are split, in either flag state, grants the policy role USAGE on the schema, SELECT/INSERT/UPDATE/DELETE on each existing managed table, SELECT on `compression_metadata`, USAGE/SELECT on the sequences those tables own and EXECUTE on `jsonb_merge_patch`, missing ones only, under the advisory lock only when something is missing; a missing policy role refuses with the `CREATE ROLE`/`GRANT` statements) and `apply_rls` (`app/migrations/rls.py`, flag on: double-checked locking over `rls_state.py`'s lock-free `read_rls_state`/`plan_rls`, so a boot whose `sha` and `def` fingerprints, ENABLE flags and view ACL all match issues no DDL and takes no lock; otherwise it repairs only what differs under the lock, with a WARNING naming every object edited out of band and every view grantee it revokes, re-creating the view when a column or the policy role changes; a policy whose rendered definition changed between releases, such as the grants read and insert policies gaining the owner arm, is STALE and a newly added one, such as the grants delete policy, MISSING, and both are repaired with an INFO line and no WARNING, the helpers' EXECUTE grants following `helper_functions`). Tables created later (node summaries switched on, a vector table re-created by `--compress`/`--decompress`) get their policies and grants on the next boot. `remove_rls` (`rls_removal.py`, the `--disable-rls` CLI) drops everything ours and disables RLS only where `preenabled=false`. The FTS language rebuild (`FtsRepository.migrate_language`) drops the read view before its DROP COLUMN and re-creates it in the same transaction (`create_read_view`) only when it existed.

**Embedding storage is provisioned from `ENABLE_EMBEDDING_GENERATION`, decoupled from the search-tool toggles.** The vec tables and chunk columns (`app/migrations/semantic.py`, `app/migrations/chunking.py`) gate on `settings.embedding.generation_enabled` (default true), NOT on `settings.semantic_search.enabled` — with an INFRA-PRESENT FALLTHROUGH shared with the compression migration (probe: `app/migrations/_probes.py` `embedding_metadata_table_exists`, `to_regclass`/search_path resolution on PostgreSQL): a generation-off database whose `embedding_metadata` table exists keeps its ACTIVE-format payload table provisioned (fp32 when compression is off, compressed when on), because the delete/update cleanup paths gate on that table's presence and then touch the active payload table; only a FRESH generation-off database skips. The PostgreSQL pgvector pre-create AND the vector-codec registration (gated together on `self._provision_vector`, decided by `_resolve_provision_vector` in `app/backends/postgresql_backend/provisioning.py`) run exactly when the fp32 layout will be provisioned or already exists: generation on with compression off provisions without a probe; otherwise a probe (after `apply_session_gucs`, so through the configured search_path) provisions iff `vec_context_embeddings` exists or, with compression off, iff `embedding_metadata` exists. A generation-off infra-carrying database whose pgvector extension was dropped therefore re-creates it before the semantic migration's `CREATE TABLE ... vector(dim)` runs (without it boot fails on `type "vector" does not exist`), and a compressed deployment without an fp32 table never needs pgvector. A probe connect fault propagates into `initialize()`'s classification ladder; the migration CLI bypasses the gate with the `provision_vector` constructor override. The SQLite semantic migration skips its `sqlite_vec` import when `skip_fp32_vec` stripped every vec0 statement (a compressed generation-off database needs no vec0 module). The SQLite sqlite-vec extension load (`_load_sqlite_vec_extension` in `app/backends/sqlite_backend/connections.py`) is instead UNCONDITIONAL — loaded whenever the `sqlite_vec` package is installed — because the durable stale-embedding cleanup paths gate on the `embedding_tables_exist()` table-presence signal and must reach the vec0 module even when generation is toggled off. So embedding storage exists whenever embeddings are generated, regardless of whether the `semantic_search_context` tool is exposed — turning semantic search on later never requires re-embedding, and the fp32-latent edge (generation on, semantic tool off, compression off) is closed. When `settings.compression.enabled` is true the server path additionally OMITS the fp32 `vec_context_embeddings` table + its HNSW index from `apply_semantic_search_migration`/`apply_chunking_migration` (`skip_fp32_vec`, applied via `_strip_fp32_vec_statements` on the semantic SQL and a statement-level filter on the PostgreSQL chunking DO-blocks) — provisioning only `embedding_metadata` (still required by the compressed write path) and, on SQLite, `embedding_chunks`; the compressed table replaces the fp32 one. This keeps the fp32 table from being re-created on every restart, which would leave a stray empty table + HNSW index permanently on PostgreSQL (where the compression migration early-returns) and cause create-then-drop churn on SQLite. The `force` CLI path always builds the full fp32 layout (it never runs the compression migration and provisions compression separately via `--compress`). The FTS migration (`app/migrations/fts.py`) still gates on `settings.fts.enabled`. The migrations' `force` param (CLI bypass) applies them regardless of these gates.

### Testing Strategy

**Philosophy**: Unit and repository tests use SQLite temp databases; real-server integration tests run the SAME assertions against BOTH backends through the shared parametrized harness package `tests/integration/_harness/` (`MCPServerIntegrationTest(backend='sqlite'|'postgresql', client_mode='auto'|'legacy')`, assembled in its `__init__.py` from one mixin per tool domain over `HarnessCore` in `core.py`, which owns the client, the server environment, the result list and the helpers every mixin shares: `_outcome`, a tool call that returns the error text instead of raising, through the primary client or the one passed as `client=`, and `_record`, which records a check from its problem list; `run_all_tests` there fixes the execution order) — driven by `tests/integration/sqlite/test_real_server.py` (SQLite) and `tests/integration/postgresql/test_real_server.py` (PostgreSQL on docker-compose pgvector, isolated DB), each of which runs the full harness once per MCP protocol era (the PostgreSQL entry point also once per era with RLS on: `pg_rls_db`, requests as `mcp_app`, migrations as `mcp_owner`): `client_mode='auto'` negotiates the sessionless 2026-07-28 era (no initialize handshake, and `ping` is not routed there) and `'legacy'` the initialize-handshake era that clients such as Claude Code use. Every harness client is built by `HarnessCore._new_client`. ### Integration Testing (REQUIRED — run it, do not skip)

Changes to tool registration, search (keyword/FTS/semantic/hybrid), embeddings, summary, compression, the storage backends, or deployment MUST be validated with integration testing — never sign off on `uv run pytest -m "not integration"` alone. Two complementary mechanisms; run both when a change is relevant.

**1. pytest integration suite** (automated, self-managed containers): `uv run pytest -m integration`. Runs the shared backend-parametrized real-server harness against SQLite (stdio server subprocess) and PostgreSQL (an ephemeral pgvector container the `pg_test_url` fixture starts from `tests/integration/postgresql/docker-compose.test.yml`, gated by `@requires_docker_postgres`). Requires Docker; PostgreSQL cases skip automatically when Docker is absent. The fixture runs that container under a compose project named per checkout (`_project_name_for` in `tests/integration/postgresql/conftest.py`: a hash of the repository root), so PostgreSQL test runs in two checkouts of the repository (separate clones or linked working trees) can run at the same time without removing each other's container. Within one checkout only the session that brought the container up removes it at session end (`SESSION_CONTAINER` in the same conftest), so a `-m "not integration"` run can finish beside a running PostgreSQL session; two sessions that both run PostgreSQL tests in one checkout still remove each other's container, so run those one at a time. Its data directory is tmpfs, so `initdb/02-roles.sql` creates the RLS test roles on every start.

**2. Live deploy-stack end-to-end** (the real built Docker image served over HTTP, with real Ollama embeddings/summary/reranking, on both backends). Build and start BOTH stacks — they use distinct ports and compose project names (`context-server-sqlite-test` on :8001, `context-server-postgresql-test` on :8002) and are fully isolated from any production `context-server` stack (default :8000), which you MUST NOT touch, rebuild, or tear down. Always bring up both: skipping the PostgreSQL stack leaves the cross-backend surface unverified (a recurring failure mode — do not let the test PostgreSQL stack go missing). They run concurrently:

```bash
docker compose -f deploy/docker/docker-compose.sqlite.ollama.test.yml up -d --build      # SQLite, HTTP on :8001
docker compose -f deploy/docker/docker-compose.postgresql.ollama.test.yml up -d --build  # PostgreSQL + Ollama, HTTP on :8002
```

These two compose files are intentionally SELF-CONTAINED: they carry no `env_file` block, and every variable that exercises the feature surface — plus the PostgreSQL credentials — is hardcoded inline (NOT `${VAR:-default}`), so a developer's `deploy/docker/.env` cannot redirect providers/models or inject production credentials even though Docker Compose still auto-loads that `.env` from the compose directory for `${VAR}` interpolation. The hardcoded set: `ENABLE_SEMANTIC_SEARCH=true`, `ENABLE_FTS=true`, `ENABLE_HYBRID_SEARCH=true`, `EMBEDDING_PROVIDER=ollama` + `OLLAMA_HOST` + `EMBEDDING_MODEL`/`EMBEDDING_DIM`, `EMBEDDING_QUERY_INSTRUCTION` (the recommended qwen3 instructed-query prefix, as a double-quoted YAML scalar so `\n` becomes a real newline), `SUMMARY_PROVIDER`/`SUMMARY_MODEL`, `RERANKING_CACHE_DIR`, and (PostgreSQL stack only) the app's `POSTGRESQL_USER`/`POSTGRESQL_PASSWORD` = `mcp_app`/`mcp_app`, `POSTGRESQL_MIGRATION_USER`/`POSTGRESQL_MIGRATION_PASSWORD` = `postgres`/`postgres`, `POSTGRESQL_DATABASE=mcp_context`, `ENABLE_POSTGRESQL_RLS=true` and `POSTGRESQL_RLS_POLICY_ROLE=mcp_context_request`, while the pgvector sidecar and the one-shot `postgres-roles` service use `postgres`/`postgres`/`mcp_context`; embedding generation, chunking, reranking, summary, and compression stay default-on. ### Test Directory Structure

Tests mirror `app/`: `tests/<name>/` → `app/<name>/` (package) or `app/<name>.py` (module).

**Non-trivial mappings**:
- `tests/core/` → `app/*.py` small utility root modules (models, errors, fusion, instructions, etc.)
- `tests/server/` → `app/server.py` (dedicated directory; large/complex root modules get their own)
- `tests/integration/_harness/` → shared backend-parametrized real-server harness package: `core.py` (`HarnessCore`: state, client and second-server setup, result extraction; the protocol-era names `ClientMode`/`CLIENT_MODES`/`ERA_PROTOCOL_VERSIONS`), one `<domain>.py` mixin per tool domain or concern, and `__init__.py` assembling `MCPServerIntegrationTest` with the `run_all_tests` runner; imported by the per-backend entry points, and no module is named `test_*`, so pytest does not collect it directly
- `_<name>.py` modules inside a test package (e.g. `tests/backends/postgresql_backend/_builders.py`) → helpers shared within that package, named so pytest does not collect them; helpers shared across packages live in `tests/helpers.py`
- `conftest.py` inside a test directory (e.g. `tests/tools/context/conftest.py`) → fixtures shared by several modules of that directory. A fixture is autouse there only when every module in the directory needs it (`tests/reranking/conftest.py`, `tests/integration/postgresql/non_default_schema/conftest.py`); otherwise it stays non-autouse and each module that needs it either requests it with `pytestmark = pytest.mark.usefixtures(...)` (`tests/migrations/conftest.py`) or keeps its own autouse thin wrapper around a helper context manager (`tests/tools/batch/_mocks.py`), so no other module in the directory gains it
- `tests/integration/sqlite/` and `tests/integration/postgresql/` → per-backend real-server entry points and backend-specific tests (no app mirror); PostgreSQL gated on `@requires_docker_postgres`

**Shared infrastructure** stays at `tests/` root: `conftest.py`, `helpers.py`, `run_server.py`, `__init__.py`.

**Placement rule**: follow the PRIMARY source module under test; use import analysis as arbiter when ambiguous.

### Key Implementation Details

1. **Python 3.12+ Type Hints**: `str | None` syntax, `StrEnum`, TypedDicts in `app/types.py` (the response TypedDicts of the discovery tools `list_threads` and `get_statistics` live in `app/discovery_types.py`, and the sync tools' in `app/ingest.py` with the protocol they describe, which the CLI imports). **NEVER** use `from __future__ import annotations` in server.py (breaks FastMCP).

2. **FastMCP Tool Signatures**: `Literal["user", "agent"]` for source, `Annotated[type, Field(...)]` for docs, and no fastmcp `Context` parameter: tools send no MCP client log notifications (`ctx.info` and friends), because the protocol deprecated the logging capability as of 2026-07-28 (SEP-2577) and the SDK emits `MCPDeprecationWarning` on every send. Returns must be serializable dicts/lists. Register via `register_tool()` in `app/startup/tool_registration.py` (called from `lifespan()`), not `@mcp.tool()`.

3. **Async Operations**: SQLite ops are sync callables wrapped via `execute_write`/`execute_read`; PostgreSQL ops are native async. Repositories detect the backend via `self.backend.backend_type`.

4. **Design Patterns**:
   - **Protocol** (`@runtime_checkable`): `StorageBackend`, `TransactionContext`, `EmbeddingProvider`, `SummaryProvider`, `RerankingProvider`.
   - **Repository**: all SQL in `app/repositories/`, never in server.py or tools.
   - **Factory**: `create_backend()`, `create_embedding_provider()`, `create_summary_provider()`, `create_reranking_provider()` — dynamic imports via `PROVIDER_MODULES` dicts.
   - **DI**: `RepositoryContainer` injects all repositories.

5. **Error Classification** (`app/errors.py`): `ConfigurationError` (exit 78, supervisor never retries), `DependencyError` (exit 69, may retry with backoff). `classify_provider_error()` classifies embedding/summary provider failures. BSD sysexits.h codes for Docker/K8s restart policies.

6. **Server Instructions**: optional `instructions` field in MCP `InitializeResult`. Via `MCP_SERVER_INSTRUCTIONS` (overrides `DEFAULT_INSTRUCTIONS` from `app/instructions.py`); empty string disables. Includes a `## Skill Integration` section pointing agents to context-server Skills.

7. **UUIDv7 ID Generation** (`app/ids.py`): single source of truth for context-entry IDs. Public: `generate_id()`, `generate_id_with_timestamp(created_at)`, `normalize_id(value)`, `is_id_prefix(value)`, `resolve_prefix(prefix, repo)`.

   - **`uuid_utils.uuid7` parameter contract**: `timestamp` is UNIX **SECONDS** (integer), `nanos` the nanosecond fraction within that second. Migration CLI uses `seconds = int(created_at.timestamp())`, `nanos = created_at.microsecond * 1_000`. Passing milliseconds in `timestamp` shifts the embedded timestamp ~1000x into the future ([uuid-utils#73](https://github.com/aminalaee/uuid-utils/issues/73)).
   - **Lex-string ordering**: UUIDv7 hex sorts chronologically at MILLISECOND granularity (first 48 bits = `unix_ts_ms`; sub-millisecond order is the generator's own strategy and nothing relies on it), so the `id > ?` interleaving check stays monotonic for timestamps >= 1 ms apart.
   - **Lowercase invariant**: `normalize_id` always emits lowercase hex. Under SQLite TEXT BINARY collation uppercase `A-F` sorts before lowercase `a-f`, so mixed-case IDs would corrupt `id > ?` ordering. Tools accept either case; storage is canonical lowercase.
   - **Public display format**: 32-char hyphen-free lowercase hex (e.g. `0190abcdef1234567890abcdef123456`); tools also accept the 36-char hyphenated form via `normalize_id`. Prefix lookup requires 8 to 31 hex characters.
   - **asyncpg `pgproto.UUID` quirk**: asyncpg returns UUID columns as its own `asyncpg.pgproto.pgproto.UUID`, NOT `uuid.UUID`. Detect with `isinstance(x, uuid.UUID)` (asyncpg subclasses it) — MUST NOT use `type(x) is uuid.UUID` (fails at runtime).
   - **Future stdlib `uuid.uuid7()` (Python 3.14)**: parameterless, so unusable by the migration CLI (which needs deterministic generation from a specific `created_at`); `uuid_utils` stays the canonical migration-CLI generator.

8. **Backend identity**: request code passes the caller's scope as `access_scope`, maintenance code (migrations, startup, CLI, compression provenance) `MAINTENANCE`. `SYSTEM_SCOPE` presumes the maintenance connection on PostgreSQL: an RLS request backend binds no identity for it and would return public rows only (see "Access Scoping").

Every PostgreSQL mode, the UUIDv7 migration's source and target included, builds its backend through `app/cli/_backend.py::make_backend` (`create_maintenance_backend(connection_string=...)`: the URL credentials, no migration override; a direct `create_backend` under `app/cli` fails a structural test) and runs `assert_maintenance_connection` (`row_security_active()` over the managed tables) before any data statement; a filtered role, or a 42501 at any point, exits 1 with the owner remediation (`owner_refusal`). `--reassign-owner` rewrites `context_entries.owner_id` from FROM to TO in one raw-SQL statement (no scope type involved; both values are bound parameters with no charset limit, so it is the route for IdP subjects outside `SAFE_PRINCIPAL_ID_PATTERN` such as Auth0 `auth0|...`), sets `updated_at`, leaves `version` untouched and keeps every grant (on PostgreSQL the composite FK cascades the new owner into each grant's `entry_owner_id`, so the new owner manages them under RLS; `granted_by` keeps naming the grantor, by design an audit record), prints the matching count under `--dry-run`, and treats zero matches as a success no-op; FROM == TO or an empty value exits 1, an exception exits 2. Run it with the server stopped. It is mutually exclusive with `--compress`/`--decompress`/`--re-embed`/`--disable-rls` (argparse mode group) and returns before `--embed-missing`; so does `--disable-rls`.

The `mcp-context-ingest` console script keeps a directory of documents in sync with the thread `kb:<corpus>` of a RUNNING server: it is a pure MCP client over Streamable HTTP only (`--server URL`), so scoping, RLS and generation-first integrity apply to its writes unchanged, and it imports NEVER `app.settings`, `app.backends`, `app.repositories`, `app.tools` or `app.server` (`tests/cli/ingest/test_isolation.py`), so the operator's shell configuration is never read. The token comes from `--token-file` (re-read before every request; one retry of a 401 after the file rotated) or `--token-env NAME` (read once), never argv. A run walks the corpus (case-sensitive include/exclude matching on every host, `.git` skipped, symlinks not followed, CRLF/CR to LF), preflights the server (the four tools plus `store_context`'s `deduplicate` property), plans in slices of at most 1,000 `source_id`s, stores creates with `store_context_batch` and `deduplicate: false`, applies updates with `update_context_batch` (full metadata replacement, never a patch), deletes LAST by `context_ids` (never `thread_ids`), and verifies with a final plan. `--concurrency N` (default 1, at most 20) keeps up to N create and update batch calls in flight, each on a session of its own because one `IngestClient` carries one call at a time (its `StatusRecorder` classifies an exchange by the session's latest response, and a lost connection closes the session; a further session reading `--token-file` gets its own `TokenFileAuth`), in `app/cli/ingest/sessions.py`: batches start in order, a failed batch never cancels one in flight, a run-ending failure stops the batches not yet started while the running ones finish, the outcomes are recorded in batch order and per-entry results matched by index, so counts, report and exit code equal a sequential run's; plans and deletes stay on the first session, one call at a time. An unreadable, undecodable, empty or over-budget file becomes a keep item (its stored entry survives), a `source_id` above 256 characters is excluded, and a directory the walk cannot list withholds every delete of that run; exit codes 0 converged, 1 partial, 2 configuration/authentication/plan error, 69 transient (precedence 2 > 69 > 1). No client image ships: the server image carries the script, so the docs show `docker compose run --rm --no-deps --entrypoint mcp-context-ingest` and `uvx --from mcp-context-server mcp-context-ingest`. Full guide: `docs/knowledge-base.md`.

## CI and Docker Lock File Discipline

`uv.lock` is a UNIVERSAL resolution of ALL dependencies across ALL optional groups/extras; `uv sync` with selective flags installs only the relevant subset.

**Three defense layers**: (1) pre-commit `uv-lock` hook (local); (2) `uv lock --check` (CI early step); (3) `uv sync --locked --all-extras --all-groups` (CI install). Every CI workflow (`test.yml`, `lint.yml`) MUST run both CI steps:

```yaml
# CORRECT
- run: uv lock --check
- run: uv sync --locked --all-extras --all-groups

# WRONG: Explicit listing misses extras when new ones are added
- run: uv sync --locked --dev --extra embeddings-ollama --extra reranking
```

**Exception**: `publish.yml` and `release-please.yml` run `uv lock` (without `--check`) — Release Please bumps the version, requiring lock regeneration.

**Docker** MUST use `--locked --no-dev --extra <variant>` for SELECTIVE installation:

```dockerfile
uv sync --locked --no-install-project --extra ${EMBEDDING_EXTRA} --extra ${SUMMARY_EXTRA} --extra reranking --no-dev
uv sync --locked --extra ${EMBEDDING_EXTRA} --extra ${SUMMARY_EXTRA} --extra reranking --no-dev
```

Build args: `EMBEDDING_EXTRA` (default `embeddings-ollama`), `SUMMARY_EXTRA` (default `summary-ollama`). Docker intentionally does NOT use `--all-extras`.

### Docker Compose File Naming Convention

**Naming formula:** `docker-compose.{storage}.{providers}[.local].yml`

- `{storage}`: `sqlite`, `postgresql`, or `postgresql-external`.
- `{providers}`: embedding+summary combo — single name when both share a provider (`ollama`, `openai`), hyphenated `<embedding>-<summary>` when they differ (`ollama-openai`).
- `.local` (optional): present ONLY for combinations with a published GHCR image, marking the file that builds that config locally instead of pulling from the registry.

**Image sources**: `*.ollama.yml`/`*.ollama-openai.yml` pull the prebuilt GHCR image (`ghcr.io/getactionspace/mcp-context-server:latest` / `:latest-ollama-openai`, `pull_policy: always`); `*.local.yml` and provider-specific `*.openai.yml` build locally (`image: mcp-context-server`, `pull_policy: build`, with `EMBEDDING_EXTRA`/`SUMMARY_EXTRA` build args, e.g. `SUMMARY_EXTRA=summary-openai`).

**Extensibility rule:** if a GHCR image is published for a combo, create both `*.{providers}.yml` (pull) and `*.{providers}.local.yml` (local build); otherwise create only `*.{providers}.yml` (local build, no `.local` variant).

### Docker-Compose Environment Variable Policy

**CRITICAL:** Compose files MUST contain ONLY variables REQUIRED for the deployment to function; all else uses `app/settings/` defaults. This prevents drift between code defaults and hardcoded compose values.

**Configurable** via `${VAR:-default}` interpolation (the default MUST be the value the file would otherwise hardcode, so an unset variable keeps the standard deployment): `LOG_LEVEL`, `EMBEDDING_MODEL`, `EMBEDDING_DIM`, `EMBEDDING_PROVIDER`, `SUMMARY_MODEL`, `SUMMARY_PROVIDER`; PostgreSQL variants add `POSTGRESQL_USER`, `POSTGRESQL_PASSWORD`, `POSTGRESQL_DATABASE`. Ollama sidecar model names use the same interpolation. `POSTGRESQL_MIGRATION_USER` and `POSTGRESQL_MIGRATION_PASSWORD` are the PostgreSQL sidecar's bootstrap credentials only, interpolated with the nested defaults `${POSTGRESQL_MIGRATION_USER:-${POSTGRESQL_USER:-postgres}}` and `${POSTGRESQL_MIGRATION_PASSWORD:-${POSTGRESQL_PASSWORD:-postgres}}`, while the bundled app environment stays single-role with RLS off (no `ENABLE_POSTGRESQL_RLS` or migration variable; enabling is the override documented in `docs/deployment/docker.md`, "Enabling row-level security").

**Required (hardcoded, NOT configurable)**: transport (`MCP_TRANSPORT`, `FASTMCP_HOST`, `FASTMCP_PORT`), `FASTMCP_ENABLE_RICH_LOGGING=false`, storage backend selection, `OLLAMA_HOST` (sidecar bind + client URL), `OLLAMA_KEEP_ALIVE=-1`, feature toggles (`ENABLE_*`), container paths (`DB_PATH`, `RERANKING_CACHE_DIR`), Docker networking (`POSTGRESQL_HOST`, `POSTGRESQL_PORT`).

**Do NOT add**: tuning parameters or feature-specific settings that have correct defaults.

## Critical Implementation Warnings

### Environment Variables — Centralized Configuration

**Never use `os.environ`/`os.getenv()` directly** — always `get_settings()` from `app.settings`. Use `Field(alias='ENV_VAR_NAME')`. The one exception is the `mcp-context-ingest` client (`app/cli/ingest/`), which must NEVER import `app.settings` and reads only the variable the operator names with `--token-env`, which is its input, not server configuration.

```python
# WRONG: os.getenv('DB_PATH')
# CORRECT: get_settings().storage.db_path
```

### Context Identifier Normalization

`app/ids.py.normalize_id` is the canonical boundary normalizer for context-entry IDs. Any code accepting a `context_id` from outside the storage layer (tool parameters, CLI flags, JSON payloads) MUST route it through `normalize_id` to fold case, strip whitespace, and validate format. The lowercase-hex invariant is load-bearing for SQLite TEXT BINARY ordering — see Key Implementation Details #7.

### Settings Singleton Caching (`@lru_cache`)

`get_settings()` is `@lru_cache`-decorated — a process-lifetime singleton; once called, env var changes are ignored.

**In tests**, call `get_settings.cache_clear()` after changing env vars (e.g. after `monkeypatch.setenv(...)`) so the next `get_settings()` rebuilds `AppSettings`. For modules that change settings across tests, use an autouse fixture calling `get_settings.cache_clear()` (pattern: `tests/reranking/conftest.py`).

**Anti-pattern: Premature `get_settings()` in subprocess scripts.** `tests/run_server.py` configures environment via `os.environ` (intentional: an env configurator, not a consumer). Call `get_settings.cache_clear()` after all `os.environ` changes before launching, or utilities like `is_ollama_model_available()` cache stale defaults.

### Per-test environment overrides for module-level `settings` bindings

Tool modules cache `settings = get_settings()` at import time (e.g., the module-level `settings` binding in `app/tools/context/store.py`). To flip an env-driven setting per test: `monkeypatch.setenv(...)`, then `get_settings.cache_clear()`, then `monkeypatch.setattr(<tool_module>, 'settings', get_settings())`. The final `setattr` refreshes the module-level binding to the new singleton; without it the module keeps the stale reference. (Refactoring 15+ modules to call `get_settings()` per function would be YAGNI.) Lifespan phases (`app/startup/database_setup.py`, `providers.py`, `tool_registration.py`) bind no module-level `settings`: `lifespan()` passes `app.server.settings` to them, so patching that one binding reaches every phase.

### Settings Class Architecture

**AppSettings must NEVER contain settings fields directly** — it only composes nested settings classes. When adding settings: (1) add to an **existing** class if it EXACTLY matches the domain; (2) else create a **new** class — even for a single setting.

```python
# WRONG: my_new_setting: str = Field(...) directly on AppSettings
# CORRECT: dedicated class, composed in via default_factory
class MyFeatureSettings(CommonSettings):
    enabled: bool = Field(default=False, alias='ENABLE_MY_FEATURE')

class AppSettings(CommonSettings):
    my_feature: MyFeatureSettings = Field(default_factory=MyFeatureSettings)
```

Settings classes live in the `app/settings/` package, one domain group per module: `base.py` (`CommonSettings`, `FeatureToggleSettings`), `server.py` (logging, tool management, transport, instructions), `auth.py` (`AuthSettings`, `AccessControlSettings`, `SAFE_PRINCIPAL_ID_PATTERN`, `SAFE_PG_ROLE_PATTERN`), `storage.py` (`StorageSettings`), `providers.py` (`OllamaSettings`, `LangSmithSettings`), `embedding.py` (`EmbeddingSettings`, `ChunkingSettings`, `CompressionSettings`), `summary.py` (`SummarySettings`, `IndexTreeNodeSummarySettings`), `search.py` (search, semantic, FTS, hybrid, FTS passage, reranking, retrieval), `navigation.py` (grep, range, navigation), `sync.py` (`ContextSyncSettings`, `ENABLE_CONTEXT_SYNC`). `AppSettings` and `get_settings()` are defined in `app/settings/__init__.py` and are the only names imported from `app.settings`; import a domain class from its module (`from app.settings.storage import StorageSettings`), because mypy's `implicit_reexport = false` rejects the package-level form. A new class goes into its domain module (a new module for a new domain) and is composed into `AppSettings`. `StorageSettings` extends `BaseSettings`, the search, navigation and sync toggle classes (`SemanticSearchSettings`/`FtsSettings`/`HybridSearchSettings`/`GrepContextSettings`/`ContextNavigationSettings`/`ContextRangeSettings`/`ContextSyncSettings`) extend `FeatureToggleSettings`, the rest extend `CommonSettings`.

### Adding New MCP Tools

### Generation-First Transactional Integrity

**CRITICAL**: when generation is enabled and fails, NO data is saved — the transaction rolls back. All generation runs OUTSIDE the transaction, then all DB ops happen in one atomic `begin_transaction()` (all repo writes accept optional `txn: TransactionContext`). On the hot single-entry store/update path `run_generation` in `app/tools/_generation.py` runs three CONCURRENT legs: (1) embedding→compression (`embed_then_compress`, ABORT-MANDATORY), (2) the flat document summary (`generate_summary_with_timeout`, ABORT-MANDATORY), and (3) the index_tree per-node summaries (`_nodes_after_summary`, never-raise), which start right after the flat summary and overlap the embedding leg. `generate_embeddings_with_timeout`/`generate_summary_with_timeout` remain the single sources of truth for the embedding and summary timeout/semaphore. The embedding leg embeds a chunked text in batches through `embed_in_batches` (`app/embeddings/batching.py`), one provider request per batch with a per-batch budget: the provider retries and `compute_embedding_total_timeout()` apply to each batch, and each batch holds its own `_embedding_semaphore` slot, released between batches, so a waiting caller is served after the current batch of a running document; a failed or timed-out batch still aborts the whole entry, its message naming the batch and the chunks embedded so far. `run_generation` (the three-leg overlap) is used by the single-entry `store_context` and `update_context` paths only; the batch tools (`store_context_batch`, `update_context_batch`) do NOT call it — they reuse the same lower-level `generate_*_with_timeout` helpers in a sequential per-entry pass (embedding+summary gather, then `generate_compression_with_timeout`, then a separate `generate_index_nodes_with_timeout` node pass), because their per-entry / non-atomic error model collects per-entry failures instead of raising the combined abort `run_generation` does. The two abort-mandatory legs are awaited with their errors collected, so a failure of either raises a DETERMINISTIC combined `ToolError`: `Generation failed after exhausting configured retries: embedding: ...; summary: ...`. On any such abort the never-raise node leg is CANCELED and awaited before the transaction opens (no orphaned model call, no waiting out node timeouts); its `CancelledError` is coerced to `None` (preserve existing node rows). Generation-first integrity is UNCHANGED: any embedding, compression, or flat-summary failure means nothing is saved, while a node-summary failure/timeout never aborts the store.

**NEVER propose "graceful skip" of generation when generation is enabled.** If `ENABLE_EMBEDDING_GENERATION=true` and embeddings fail, or `ENABLE_SUMMARY_GENERATION=true` and summary fails, the entry MUST NOT be saved — no "store without embeddings"/"store without summary" fallback exists. This is non-negotiable. Skipping requires the user to explicitly set `ENABLE_EMBEDDING_GENERATION=false` or `ENABLE_SUMMARY_GENERATION=false`; only the user can make this decision.

### Access Scoping

**CRITICAL**: every read, existence probe, dedup lookup, aggregate, update and delete operates only on rows the calling principal may access, on SQLite and PostgreSQL alike, enforced in the APPLICATION layer on both backends and, on PostgreSQL with `ENABLE_POSTGRESQL_RLS=true`, ALSO in the database by row-level security (see "Database Schema"); the app predicate stays in every statement either way. The caller's scope is `AccessScope(principal_id, groups, *, may_publish=False, may_write=False)`, built ONCE per tool call (`resolve_access_scope()`, or `resolve_write_scope(principal)` in the write tools, which sets `may_publish` and `may_write`; only the RLS bind reads them, never a predicate; `may_write` defaults to False and fails closed, so a hand-built test scope that INSERTs into `context_entries` under `RlsRequestProfile` without `may_write=True` is refused 42501, the intended signal); stdio, `none` and `simple_token` all run as `(ACCESS_CONTROL_DEFAULT_PRINCIPAL, {})`, which owns every backfilled and no-token row, so single-principal deployments see no change. `build_access_predicate(scope, *, mode, backend_type, outer, start=1)` in `app/access_scope.py` emits one parenthesized fragment:

- **READ**: `<outer>.owner_id = P OR <outer>.visibility = 'public' OR` a `read` or `write` grant naming P or one of its groups.
- **WRITE**: `<outer>.owner_id = P OR` a `write` grant.
- **OWNER**: `<outer>.owner_id = P`.

The grant arm carries NO visibility condition (grants work under `private`; a write grant implies read) and correlates on `g.context_entry_id = <outer>.id`. Groups bind as ONE parameter (PostgreSQL `= ANY($n::text[])`, SQLite `IN (SELECT value FROM json_each(?))`), so the bind count is constant per mode on both backends (3 READ, 3 WRITE, 1 OWNER, 0 `SYSTEM_SCOPE`), callers advance PostgreSQL placeholders by `pred.bind_count`, and an empty group set never yields `IN ()`. `build_readable_parent_predicate(scope, *, child_key, parent_key, backend_type, start=1)` renders READ for a child row as `<child_key> IN (SELECT ce.<parent_key> FROM context_entries ce WHERE <READ>)` with the READ parameters (empty for `SYSTEM_SCOPE`); the SQLite statistics counts use it (see "Access-control columns"). `build_policy_predicate(mode, *, outer, schema)` renders the same three modes for the policies over the helper functions, and `build_gated_read_predicate(*, outer, schema, gate)` the READ mode for the read view with the role gate folded into its operands, both through the one private arm composer `_compose` that `build_access_predicate` uses, so the database and the app predicate cannot drift.

Rules:

- `scope` is keyword-only and REQUIRED with NO default on every scoped repository method and on the tool helpers `resolve_prefix`, `resolve_or_normalize_id(s)`, `semantic_search_raw`, `fts_search_raw`, `execute_store_in_transaction`, `execute_update_in_transaction`, `reread_entry_version`, `delete_entries_with_cleanup` and `_run_owned_grant_change` (the grant seams take `scope: AccessScope`). A signature change updates every app AND test call site in the same change (`tests/helpers.py::LOCAL_SCOPE` is the test default principal).
- The predicate NEVER passes through `MetadataQueryBuilder`, `count_applied_filters` or `get_filter_count`: it is appended AFTER the metadata and tag clauses and BEFORE ORDER BY / LIMIT / OFFSET / GROUP BY in every statement — ranked legs (fp32, compressed candidates AND the compressed hydration, FTS inner subquery), top-N aggregates and keyset grep pages included. NEVER post-filter scoped results in Python: hidden rows must not consume a page slot, the rank depth or a top-N position.
- Child rows (tags, images, index nodes, embedding existence) are read only by ids a READ-scoped parent read produced in the same request; the completeness test pins every child reader and writer call site.
- Unreadable equals absent everywhere (membership, counts, messages, prefix match and ambiguity); readable-but-not-authorized is an explicit `EntryNotAuthorizedError` (`app/tools/_transactions.py`, a breaker-exempt `ControlFlowError`). WRITE and OWNER are re-asserted inside the mutating statement or transaction; the pre-generation probe only saves generation spend.
- `SYSTEM_SCOPE` is never built from request data and never referenced under `app/tools/`; its only runtime consumer is the FTS migration's record count (`app/migrations/fts.py`), which runs on the maintenance backend. CLI paths (`app/cli/`) run raw SQL as the table owner through `make_backend` with `MAINTENANCE` and no repository scope.
- **Backend access seam**: `execute_read`, `execute_write` and `begin_transaction` take a REQUIRED keyword-only `access_scope: BackendAccess` (`AccessScope | SystemScope | MaintenanceAccess`). Repositories pass `access_scope=scope`, tools pass their scope to `begin_transaction`, and migrations, startup (`tool_registration`'s `repos.fts.is_available(scope=MAINTENANCE)` included), `app/startup/__init__.py` raw SQL and `app/compression/provenance.py` pass `MAINTENANCE`, which never appears under `app/tools` or `app/repositories`. SQLite discards it (`_ = access_scope`); PostgreSQL hands it to the session profile. GUARDED methods (the predicate seams SCOPED, WRITE_AUTHORIZED, OWNER_KEYED, plus OWNER_STAMPED) keep `scope: Scope` (`AccessScope` for OWNER_KEYED and OWNER_STAMPED) and never admit `MAINTENANCE`; a CHILD_BY_TRUSTED_ID, CHILD_WRITER or SYSTEM method that itself calls a backend entry point takes `scope: BackendAccess` and forwards it; a method that only runs on a caller's `txn` takes none. `get_connection` is never called outside `app/backends`, because a raw connection cannot carry an identity.
- **Read routing**: every plain SELECT of a GUARDED or CHILD_BY_TRUSTED_ID method (and of their ranked closures) names each ROUTABLE table (`context_entries` and every child table; not the grants table) through `self._readable(table, alias=<the alias its columns and predicate use>)`; INSERT/UPDATE/DELETE targets, locking reads (`entry_exists`'s `FOR KEY SHARE`), CHILD_WRITER and SYSTEM methods name base tables. The base form keeps the alias (`context_entries ce`) and `RlsRequestProfile` maps only `context_entries` to `context_entries_readable AS <alias>`, so name resolution is identical in every profile and an alias mismatch fails the RLS-off suites too. SQLite output is unchanged.
- **Read view and identity** (RLS on): plain reads go through `context_entries_readable` because policies are security-barrier quals and non-leakproof operators (FTS `@@`, JSONB accessors, numeric casts) cannot be index conditions under them; the owner-owned, non-barrier view keeps every index. `RlsRequestProfile.bind` issues `BIND_IDENTITY_STATEMENT` first in every transaction (`set_config` of `app.principal_id`, `app.groups` as an exact `text[]` literal, `app.may_publish`, `app.may_write` and `jit=off`, all transaction-local, one round trip), wraps reads in a transaction, and binds nothing for `SYSTEM_SCOPE`/`MAINTENANCE` (fail closed: public rows only). No session-level fallback: it would be unsafe behind transaction poolers.
- **Totality**: the app's conditions run on rows the caller cannot read inside view reads, so every coercion of stored JSON text to a non-text type in generated PostgreSQL SQL goes through a total accessor (`pg_total_numeric`/`pg_numeric_accessor` in `app/metadata_sql.py`: NUMERIC for a JSON number, NULL otherwise) and can never raise; pinned by the cast guard and the totality matrix (see "Testing Strategy").
- Deployment-level channels stay global by design and are documented: `get_statistics` `database_size_mb`, `embeddings_size_mb`/`embeddings_size_estimated`, `connection_metrics` and the configuration blocks; the FTS migration ETA; PostgreSQL `EXPLAIN` row estimates; and SQLite FTS5 `bm25()` scores (see "Search Tools"). Every other `get_statistics` and `list_threads` figure is per caller.
- **Owner-stamped insert**: the one INSERT into `context_entries` is `_insert_entry_sql` in `dedup.py`, used by both `store_with_deduplication`'s fresh-insert branches and `insert_entry` (the `deduplicate=false` path): `owner_id` is bound from `scope.principal_id` and from nowhere else, and the seam is OWNER_STAMPED (no predicate; its own completeness rule).
- **Grant statements**: share, unshare and list are owner-only. `_run_owned_grant_change` in `app/tools/sharing.py` opens one transaction, probes with `probe_ids` (unreadable → `EntryNotFoundError`, readable but not owned → `EntryNotAuthorizedError(action='share'|'unshare')`, the owner naming itself as a user grantee → `OwnerShareError`), then runs the change; `list_context_grants` probes and lists without a transaction (`action='list_grants'`). Every grant statement also carries the OWNER predicate itself: the one INSERT builder `_grant_insert_sql` selects the entry under OWNER and binds `granted_by` from `scope.principal_id` and from nowhere else (the grantor rule), the DELETE re-asserts OWNER in an EXISTS, the list joins the routed `ce` under OWNER; the grants table is not ROUTABLE and keeps its base name. Grants never bump `version` or touch `updated_at` (see "Update Context and Batch Operations").
- **Sync reads** (`ContextIngestMixin`): `ingest_rows_in_range` (SCOPED) reads the thread's members inside `(source_id_after, source_id_through]` under READ, with the OWNER predicate's `AccessPredicate.admits_expression()` in the SELECT list as `is_owner`, so the plan manages owned rows and only counts the rest as `foreign_count`; `owned_ingest_page` (WRITE_AUTHORIZED seam) pages the caller's OWN members in `(source_id, id)` keyset order, the OWNER predicate in SQL, so a foreign row never takes a page slot. Both route through `self._readable('context_entries', alias='ce')`, decide membership (`scope == thread_id`) in SQL, never read the block for access, and on PostgreSQL bound and order the key under `COLLATE "C"` (code-point order, as SQLite `BINARY`).
- **Read-back**: every entry-carrying read response (`get_context_by_ids`, the four searches, each `grep_context` row and match, and the top level of `navigate_context` and `read_context_range`) carries `visibility` and a bool `is_owner` (the OWNER predicate's `admits_expression()`, one bind per statement, coerced by `entry_access_fields`; the search tools apply it in `apply_search_display_format`, after the fusion whitelist for hybrid), declared `Required[...]` on the `total=False` TypedDicts and pinned by `tests/core/test_types.py`. ### Deduplication Behavior (store_context)

Deduplication is **retry protection**: when an MCP client retransmits the same message (network glitch, timeout retry), the server updates the existing entry instead of duplicating. A **new conversational turn** (a user deliberately re-sending identical text after an agent responded) instead inserts a new entry, preserving chronological order. Both store tools deduplicate by default; `deduplicate=false` turns it off for one store or one batch entry (see "Opting out" below).

**Candidate (caller-scoped)**: the candidate is the latest entry of `(thread_id, source)` among the rows the caller can READ, and it is merged into only when the caller OWNS it and its hash matches; otherwise the store INSERTs a fresh row owned by the caller (a readable identical row of another principal is never merged into, and a hidden same-source row is skipped). The dedup UPDATE (`_dedup_update_sql`) re-asserts `owner_id = ?` in its WHERE. `store_with_deduplication` and the pre-check `check_latest_is_duplicate` build their candidate and interleave SQL from the shared helpers `_candidate_sql`/`_interleave_sql` in `dedup.py`, so both use byte-identical fragments; the pre-check returns `None` for a foreign candidate (no summary reuse, no embedding probe on a foreign id).

**Interleaving check**: before deduplicating, the server checks for opposite-source entries (agent for user source, user for agent source) after the candidate; if any exist it's a new turn. Only opposite-source rows the caller can READ count. Uses `id > candidate_id` (immune to clock skew) with the existing `idx_thread_source` index.

When deduplication proceeds (same `thread_id + source + text_content` as the latest readable entry, owned by the caller, no readable interleaving): **Metadata** via `COALESCE(new, existing)` (`None` keeps existing, explicit value replaces); **Tags/Images** REPLACED (not accumulated) when provided, preserved when `None`; **content_type/updated_at** auto-updated; **Embeddings** skipped if present, else generated; **Summary** regeneration skipped if present (`COALESCE(NULL, existing_summary)` preserves it); **Pre-check** read-only check before generation skips LLM calls for duplicates (in both `store_context` and `store_context_batch`).

`store_context_batch` applies the same dedup logic per entry: `store_with_deduplication`, the pre-check and the interleaving check for a deduplicating entry, `insert_entry` and no pre-check for a `deduplicate=false` one.

**Opting out (`deduplicate=false`)**: the `deduplicate` parameter of `store_context` (default `True`) and the per-entry `deduplicate` key of `store_context_batch` (absent means `True`) make the store exactly one fresh INSERT owned by the caller. The batch key is validated in `validate_store_entry` with `TypeAdapter(bool)`, the same lax coercion FastMCP applies to the single-entry parameter, NEVER truthiness: `'false'`, `'0'`, `0` and `'off'` are `False`, while `2`, `'maybe'` and `None` fail the entry with `deduplicate must be a boolean`. `execute_store_in_transaction` takes `deduplicate` as a REQUIRED keyword (no default) and calls `ContextRepository.insert_entry` instead of `store_with_deduplication`; both build the INSERT with the shared `_insert_entry_sql` in `dedup.py` (one column list, `owner_id` bound from `scope.principal_id` and from nowhere else), which the completeness test classifies as the `owner_stamped` seam. The tool layer also skips the read-only pre-check, the embedding-existence probe and summary reuse, and no candidate or interleave SELECT runs: every generation leg runs as for any new entry, so the reconcile path (`EmbeddingsReconcileRequiredError`) never fires, and generation-first integrity is unchanged. Visibility is always applied, and author-group grants, tags, images, embeddings (`upsert=False`) and node rows are written as for any fresh insert. Batch entries run in order, so a deduplicating entry after an identical `deduplicate=false` entry of the same thread and source merges into the row just inserted, which is then the latest readable, owned, identical row.

**Corpus sync** stores with `deduplicate=false`: in a single-source `kb:` thread the turn check never fires, so two different documents with identical text would merge, the second store replacing the first's metadata (ingest block included) and the first document vanishing from the sync state. Idempotent re-upload comes from `plan_context_sync` reporting unchanged documents (`unchanged_count`), NEVER from deduplication; recovery after an unknown outcome (a batch that timed out on the client) is a re-plan, NEVER a resend, because a resent `deduplicate=false` store inserts a second copy (the next plan lists such duplicates as deletes).

### Update Context and Batch Operations

**Update**: Partial updates (only provided fields). Immutable: `id`, `thread_id`, `source`, `created_at`, `owner_id`. Auto-managed: `content_type`, `updated_at`. Tags/images: replacement (not merge). `visibility`: owner-only (checked against the `check_entry_exists` probe's `owner_id`, which is immutable so the pre-generation read cannot go stale) and publish-gated for 'public'. Transaction-wrapped.

**Authorization (WRITE for content, OWNER for visibility and deletes)**: the update tools resolve the principal and scope unconditionally before prefix resolution, then probe with `check_entry_exists(..., scope=)`, whose `EntryProbe.exists` is decided by READ and whose `can_write` is WRITE computed in the same statement. Not readable → `Context entry with ID {id} not found` (batch: `Context entry {id} not found`, atomic `... at index {i}`); readable but not writable → `EntryNotAuthorizedError` → `Not authorized to modify context entry with ID {id}` (batch: `Not authorized to modify context entry {id}`), raised BEFORE any generation, for every change including a visibility change, so a caller who may only read (a read grant or a public row) never sees the owner-only text; a visibility change by a write grantee who is not the owner → `Only the owner may change the visibility of context {id}` (reachable only for rows the caller may modify). Write grantees edit text, metadata, `metadata_patch`, tags and images. Inside the transaction every write re-asserts its predicate: `update_context_entry` uses OWNER when `visibility` is set and WRITE otherwise, `patch_metadata`/`touch_updated_at`/`update_content_type`/`get_content_type` use WRITE, the tags/images-only gate `entry_exists` uses WRITE (PostgreSQL `FOR KEY SHARE OF context_entries`), and a row that became unwritable surfaces as `EntryNotFoundError` (never `VersionConflictError`; a `None` content type raises instead of issuing an id-only write).

**Deletes**: every delete runs through the one chokepoint `delete_entries_with_cleanup(repos, ids, *, scope, refuse_unauthorized)` in `app/tools/_delete_cleanup.py`: inside ONE transaction `probe_ids` (READ-filtered `IdAccess(can_write, is_owner)`) picks the owned ids, the embedding cleanup and `delete_by_ids` (OWNER in the DELETE WHERE) cover exactly those. A delete that names ids (`delete_context` with `context_ids`, `delete_context_batch` with `context_ids`, which snapshots in READ mode) passes `refuse_unauthorized=True`: a readable non-owned id raises `Not authorized to delete context entries: {ids}` and nothing is deleted, a hidden id is skipped and not counted. Thread and criteria deletes (`delete_context` with `thread_id`, `delete_context_batch` without `context_ids`) snapshot ids with `get_ids_matching_batch_criteria(..., mode=AccessMode.OWNER)` on BOTH backends and pass `False`, so they silently cover only the caller's rows.

**Optimistic concurrency guard**: because generation runs outside the transaction with variable LLM latency, `update_context`/`update_context_batch` capture the row's `version` BEFORE generation (via `check_entry_exists`, which returns an `EntryProbe(exists, source, version, owner_id, can_write)`) and do a compare-and-set on commit — `update_context_entry(expected_version=...)` adds `WHERE id=? AND version=?` and `SET version=version+1` on both backends. If a concurrent writer committed during generation the affected-row count is 0 and the repository raises `VersionConflictError` (a control-flow exception, not a `ToolError`). The single-update path re-reads the new version and retries (bounded to 5 attempts) so an older-text update can never silently overwrite a newer one (and index_tree node rows can never describe stale text); an atomic batch aborts with a clear `ToolError`; a non-atomic batch re-reads the current version and retries per entry (bounded to 5 conflicts, mirroring the single-update path), recording a per-entry failure only after exhausting those retries. The guard covers updates that change `text` or full `metadata` — the only `update_context_entry` write that runs the compare-and-set and bumps `version`. `metadata_patch`-only, `tags`-only, and `images`-only updates intentionally do NOT bump `version` or participate in the CAS, because `patch_metadata` is an atomic in-DB read-modify-write (concurrent patches compose against the committed state) and tags/images use documented replacement (last-writer-wins) semantics — none of these has a lost-update window the CAS would close, and a full-metadata replacement overwriting a concurrent patch is replacement semantics, not a lost update. A `visibility` change rides the same `update_context_entry` write, so it participates in the CAS and bumps `version` like text/metadata. For the covered updates this makes concurrent same-entry writes last-writer-by-submission instead of last-writer-by-completion, and closes a pre-existing `text_content` lost-update window on the same write path. Fresh inserts get a brand-new UUIDv7 `id`, so no concurrent writer holds it and the guard applies to update paths only.

**Grants outside the CAS**: `share_context` and `unshare_context` never bump `version`, like tag and image replacement, and never touch `updated_at` (which tag and image replacement do advance): a bump would make a concurrent write grantee's update conflict and would need the WRITE policy (pinned by `tests/tools/test_sharing.py`, the harness sharing mixin, and a test whose update captured its version before a share and still commits). No update path writes or removes grants, and deleting an entry cascades its grants. An unshare that lands mid-call surfaces as a missing entry: a write grantee's in-flight update reports not found even when the entry stays readable through another arm (under RLS a child write in that window may fail 42501 as a generic error), and `navigate_context`'s version bracket (`check_entry_exists` before and after the node read) sees the revoked probe's `version` of None, retakes the snapshot and reports `Context entry not found: {id}`, pinned by `test_navigate_unshare_inside_the_window_reports_not_found`; both residuals are documented in `docs/authentication.md` ("Enforcement and Its Limits").

**Batch**: `store_context_batch`, `update_context_batch`, `delete_context_batch` (up to 100 entries). `atomic=true` (default): all-or-nothing. `atomic=false`: independent processing with per-entry results. Batch and non-batch tools share per-entry logic for parity: image validation (`app/tools/_validation.py`), generation (`app/tools/_generation.py`), transaction execution (`app/tools/_transactions.py`), delete cleanup (`app/tools/_delete_cleanup.py`), and response building (`app/tools/_responses.py`).

### Compression Seed-Locked Invariant

`COMPRESSION_SEED` defaults to `0` in v3.0.0. On first start the validator (`app/startup/compression_validator.py`) writes a singleton `compression_metadata` row from the runtime config — including the realized `codebook_fingerprint` — then treats the DB as source of truth. Later starts where runtime `CompressionSettings` disagrees with the persisted `(provider, bits, variant, seed, dim)` row raise `ConfigurationError` (exit 78); and when those scalars match, the validator re-derives the realized `codebook_fingerprint` (SHA-256 of the `numpy.linalg.qr` rotation matrix) and ALSO raises exit 78 if it diverges — because `numpy.linalg.qr` is a LAPACK call whose low-order bits differ across BLAS/LAPACK builds and CPU dispatch, the seed alone does not guarantee a reproducible codebook across hosts, and a divergent rotation would silently corrupt every decode/search. The supervisor will NOT auto-restart, surfacing the misconfiguration loudly instead of silently corrupting search results. (A pre-fingerprint row reads as `None` and only warns — the compression migration adds the nullable column idempotently, but no code path ever backfills a fingerprint into an existing row: recording one requires re-compressing on the target host, per the warning's own guidance, because backfilling on a possibly-divergent host would seal a wrong digest.)

Both toggle DIRECTIONS are guarded against a bare env flip on a populated database: disabling compression while a provenance row exists is refused at startup (exit 78, run `--decompress` first, which clears the row), and enabling compression while fp32 `vec_context_embeddings` rows exist with NO provenance row is also refused at startup (exit 78, run `--compress` first, which encodes them) — the guard lives in `apply_compression_migration`, which would otherwise DROP the populated fp32 table on first-time application.

In multi-pod Kubernetes deployments all pods MUST inherit the SAME `COMPRESSION_SEED` (ConfigMap-bound, so every pod resolves the identical value). Changing the seed AFTER any compressed data is stored corrupts every decode/search; the only recovery is restoring from backup. The Helm chart ships an active compression block (`enabled: true`, `seed: 0`) in `values-sqlite.yaml`/`values-postgresql.yaml` under `deploy/helm/mcp-context-server/` (PG profile documents the multi-pod ConfigMap discipline inline); `compression.enabled: false` opts out. See `docs/embedding-compression.md`.

After validation, the lifespan logs the active compression config (singleton `compression_metadata` row + `max_concurrent`); when disabled it reports `Embedding compression disabled (ENABLE_EMBEDDING_COMPRESSION=false)`. `get_statistics` exposes the same values under a `compression` sub-block, plus `embeddings_size_mb` and boolean `embeddings_size_estimated` after total `database_size_mb` — gated on embedding generation OR compression (NOT `ENABLE_SEMANTIC_SEARCH`), `0.0` on failure. Both size keys are per-backend, NOT byte-comparable (formulas in `docs/embedding-compression.md#observability`; on SQLite `embeddings_size_estimated=true` marks a deterministic fp32 estimate). PostgreSQL numeric aggregates are coerced to floats via `_to_float` in `app/repositories/statistics_repository.py` (asyncpg maps `AVG()` to `Decimal`, failing the MCP float output schema).

### Upstream Workarounds

Every workaround for a third-party defect (a library, SDK, client, or service this project does not control) is tracked in the `upstream-issues` thread of the context server: one `upstream_issue` entry per defect, with `mcp-context-server` in its `affected_projects`, a labeled Workaround block naming the exact code and tests, and a Remove-when block naming the upstream change that retires it and everything to delete. Record the entry in the same change that adds a workaround, re-check this project's open entries whenever a dependency named in their `recheck_on` moves, and keep no parallel list of upstream workarounds in this repository.
